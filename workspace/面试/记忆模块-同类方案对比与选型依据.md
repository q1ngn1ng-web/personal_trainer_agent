# 记忆模块：同类方案对比与选型依据

> 更新日期：2026-10-15
> 用途：面试讲"记忆模块怎么设计、为什么不用现成框架、解决了什么场景问题"
> 证据档位：【文档口径】= 官方文档/论文所述，未在本机实测；【本仓实测】= 有代码或测试可查

---

## 一、业界主流做法可以归成三类

| 类型 | 代表 | 存什么 | 怎么查 | 适合什么 |
|---|---|---|---|---|
| 对话记忆框架 | Mem0、Zep/Graphiti、Letta(MemGPT) | 从对话里抽出来的事实、偏好、关系 | 语义召回（向量/图） | 多轮聊天、角色扮演、陪伴类 |
| 通用状态存储 | LangGraph checkpointer / BaseStore、Redis、Postgres | 会话状态、键值 | 按 key（可加语义检索） | agent 运行时状态 |
| 结构化业务状态 | 关系库 + 规则聚合 | 领域事实（作答、对错、得分、时间） | SQL 精确查询 | 任务型 agent、评测、训练类 |

**本项目的定位是第三类。** 这是理解后面所有取舍的前提。

## 二、几个框架的机制（抽象到机制层面，不背 API）

**Mem0**【文档口径】从对话中由模型抽取"事实/偏好"存进向量库（可叠加图），检索时按语义召回相关记忆再注入上下文。卖点是"比把全部历史塞进上下文省得多，且能跨会话记住用户"。

**Zep / Graphiti**【论文/文档口径】时序知识图谱：边带生效时间，能回答"某个时间点之前用户说过什么"，处理事实变更（用户搬了家）比向量更好。

**Letta（原 MemGPT）**【论文口径】把操作系统的内存分层搬过来：常驻上下文的核心记忆（模型可以自己改）、可召回的历史消息、外部的归档存储；模型通过工具调用在层之间搬数据。核心思想是**上下文窗口当内存管，用换页而不是无限扩容**。

**LangGraph**【文档口径】短期记忆 = checkpointer 按 thread 存状态；长期记忆 = BaseStore 按 namespace 存键值，可选语义检索。它把"记忆"拆成"线程状态"和"跨线程存储"两块。

**Anthropic 上下文工程**【官方博客口径】三条做法：压缩（compaction）、结构化笔记（把关键信息写到上下文之外）、子 agent 分工。

## 三、共性机制（为什么大家都这么设计）

把所有方案剥掉外壳，都在解决四件事：

1. **分层**：工作记忆（当前任务）→ 短期（本次会话）→ 长期（跨会话）。对应"哪些信息该常驻上下文、哪些该外部化"。
2. **写入策略**：抽取式（模型从原文抽事实）vs 记录式（结构化直接落库）。前者灵活、后者精确。
3. **检索策略**：语义召回 vs 结构化查询。前者能处理没说清楚的，后者能保证不漏。
4. **生命周期**：更新、冲突消解、遗忘。这是长期记忆真正的难点——同一事实变了怎么办。

**本项目四条都涉及，但取向不同**：记忆是**领域状态**而非对话文本，所以写入用记录式、查询用结构化、分层按"事实/派生/上下文"切。

## 四、为什么本项目不用现成框架

| 维度 | 用 Mem0/Zep 这类 | 本项目的选择 |
|---|---|---|
| 精确性 | 语义召回是近似的，"错过哪些题"可能漏 | `WHERE` 精确查询，必须 100% 对【本仓实测：`practice_attempts` 注释即"客观表现的唯一数据源"】 |
| 数据形态 | 面向自由文本对话 | 95% 是结构化状态（题号、分值、要点四态、时间） |
| 成本 | 每次写入要抽取、每次读取要 embedding | 规则聚合零调用；错因也能由要点判定推导 |
| 可控性 | 摘要策略黑盒，同数据两次结果可能不同 | 渲染是确定性代码，同输入同输出 |
| 架构 | 默认长会话常驻 | 服务无状态，每次从库重建上下文（可重启、可扩展） |

**唯一会轮到框架的场景**：要记的是模糊偏好（"用户喜欢用类比讲解""上次那个比喻没听懂"）——这类没有 schema 的信息才需要向量或图。本项目当前不需要。

## 五、面试怎么讲（三问三答）

**Q1：你的记忆模块怎么设计的？**

> 分三层。事实层是逐次作答记录，我把它当作唯一真相源，带分数和每条要点的判定；派生层是薄弱点画像，用纯 SQL 聚合出知识点掌握度、题型失误分布、高频错因；上下文层按需把前两层渲染成一段紧凑摘要注入提示词。关键是**不压缩原始对话，而是一开始就不产生原始对话**——信息一直在库里，用的时候渲染。

**Q2：为什么不用 Mem0 这类框架？**

> 因为场景错配。那些框架解决的是对话记忆——把聊天里的偏好和事实抽出来存向量，检索时语义召回。而我要回答的是"他在这道题上错过几次、错因是什么"，这是必须精确的查询，用近似召回是降级。而且我的记忆 95% 是结构化状态，用关系库 + SQL 是最合适的工具。另外我要求服务无状态、可重启可扩展，框架默认的长会话常驻跟这个诉求是冲突的。

**Q3：解决了什么场景问题？**

> 一个训练计划跨 30 天。用户第 24 天再错同一个知识点时，系统要能说"这是你第三次栽在 RDB/AOF 上，而且三次都是同一个错因：概念混淆"——没有记忆的话，每次点评都是从零开始。要做到这句，需要三件事：错因必须是**可聚合的枚举而不是一段自由文本**、历史错因要能被检索、评价时要把这段历史注入上下文。

## 六、差异化点（跟业界常见的比，我多做/少做了什么）

1. **错因枚举化**：对话记忆框架通常不区分"错因类型"，本项目把错因做成固定枚举，于是"同一错因出现几次"可聚合、可断言。
2. **规则优先、模型可选**：错因先由要点判定推导（零调用），LLM 深入分析做成**用户开关**——成本与隐私都可控。
3. **时间纵深注入**：评价时注入历史同类错因，而不是只给当前状态。
