# 05 · 缺陷修复实战：判分与前端六连修（面试讲法）

> 用途：面试讲"你解决过什么难题/说说你印象最深的 bug"时的弹药库。
> 纪律：每个数字都有出处（commit / evidence / 测试）；【分析】标注的是判断而非实测。
> 日期：2026-11-15 ~ 11-20｜涉及 commits：`9ee4145`/`7113ee7`/`8d6b04d`/`728c6da`/`2210268`/`36abf31`。

## 0. 一览表（先挑最有把握的讲）

## Bug 1｜同题同答，重判结果会漂移（判分一致性）

**现象**：用户标注发现，同一道题、同一份作答，重判几次结论不同——严格四态一致率 0/6（n=6，二值口径 4/6）。
而且分数横跨及格线（0.55~0.93），"连续 2 次达标"可以被重判翻转。

**排查过程**（怎么定位的）：
1. 先写对照实验脚本（`scripts/eval_grading_consistency.py`）：同一作答重判 N 次，温度 0.2 与 0 各一组；
2. 实测：温度 0.2 出现 3 种判定组合，温度 **0 仍有 4 种**——排除"采样参数"这个直觉答案；
3. 结论：波动来自**服务端非确定性**（推理批处理/路由），客户端怎么调都压不住。

**根因**：判分是概率输出，而下游（达标判定、薄弱点画像、题型配比）全建立在"逐次判分"之上——
概率输出 + 确定性下游 = 噪声放大。

**修复（两层）**：
1. 温度仍降为 0（消除客户端采样噪声，方向正确但**不足以解决问题**——如实说）；
2. **幂等判分缓存**（正解）：同一（模型, prompt 版本, 题目, 参考答案, 要点清单, 作答）
   判一次、存一次、永久逐字复现；prompt 升级键自动失效；缓存只存模型语义意见，
   分数仍由规则层实时计算。

**验证**：重复判分零模型调用、结果逐字一致（集成测试钉死）；
与人工的标注（n=6）另发现**边界口径分歧**（hit↔partial 边界为主）——如实记录为待校准项。

**面试口播（约 40 秒）**：

> 我遇到最有意思的 bug 是：同一道题、同一份作答，重判几次结论不一样——严格一致率 0/6，
> 分数能横跨及格线。我第一反应是调温度，实测降到 0 还是 4 种组合——波动来自服务端
> 非确定性，客户端压不住。所以真正的解法是幂等缓存：同模型、同 prompt 版本、同题、
> 同作答，判一次存一次，之后永久逐字复现，prompt 升级自动失效重判。缓存里存的是模型
> 的语义意见，分数仍由规则层实时算——口径升级不受旧缓存污染。另外我和自己做了一轮
> 人工标注（n=6），发现人机分歧集中在 hit 和 partial 的边界——这是已知的待校准项，
> 我没有因为 6 个样本就去改判分口径。

**追问预案**：
1. 为什么不用多数投票？——3 倍 token 且仍非确定；缓存在首次判分后就终止不确定性。
2. 缓存会不会让旧口径的分数永久错下去？——键含 prompt 版本与模型，升级自动失效；且缓存存的是意见不是分数。
3. 人工标注只有 6 条怎么讲？——明确说"初步信号"，结论是发现边界口径分歧这个**方向**，不是一致率数字本身。

## Bug 2｜客观题走了大模型（设计与接线脱节）

**现象**：一道选择题的要点被语义判成 partial——按设计它应该是零成本毫秒级的比对。
排查发现 `answer_service._grade_answer` **没有任何题型分流**：choice/fill 也被组装成
语义判分 payload 送进 LLM。ADR-0022 写着"客观题 MUST NOT 调用大模型"，
`grading_service.grade_objective` 函数也在——**但主链从来没接**。

**排查过程**：用户报告那道选择题判分诡异 → 翻判分调用链发现 payload 里连
question_type 和 options 都没有 → 确认是接线缺失，不是判分逻辑错误。

**修复**：主链按题型分流——choice/fill 走确定性判分（零模型调用），qa 走要点语义判分；
`question_type/options` 随题固化到 plan_items（此前出题后从未落库，判分时丢失）。

**验证**：新增测试断言"提交选择题全程零模型调用 + 来源落库为 rule"。

**面试口播（约 30 秒）**：

> 有个 bug 特别典型：我们的设计是客观题零模型调用、主观题才走 LLM——函数都在、
> 测试也过，但主链上选择题还是被送进了大模型。排查发现是接线缺失：判分入口没有按
> 题型分流，payload 里连题型和选项字段都没有。这让我记住一条：**设计与接线是两回事，
> 接线要有自己的审计**——我们后来把"每个判分调用必须带题型标记"做成了约定。

**追问预案**：
1. 怎么防止再发生？——判分入口强制带题型分流的约定 + 端到端测试断言零模型调用。
2. 为什么函数级测试没抓住？——函数级测试测的是判分函数本身，没测"主链是否调用了它"——分层测试的盲区。

## Bug 3｜schema 没展示给模型（防线要前移）

**现象**：模型输出首发合规率 **0/6**——每次判分都要靠"错误反馈重试"兜底，延迟翻倍。

**排查**：模板里写着"只输出 JSON，字段见 schema"——但 **prompt 里根本没有 schema**
（老 11 个模板有占位符，新 4 个漏了）。模型在盲猜输出形状。

**修复**：补占位符（老模板同款句式），实测首发合规 **6/6**；
多花 ~300 tokens 输入，换掉一整个重试往返（第二轮还要回显首答+反馈）——净省。
另加守卫测试：凡注册了 schema 的用途，模板必须展示 schema（防回退）。

**面试口播（约 25 秒）**：

> 模型输出不合规时，我们的重试机制会带着错误反馈让它自纠——但有个 bug 让我意识到
> 防线应该前移：新模板漏了 schema 占位符，模型从头到尾没见过输出格式定义，首发合规
% 实测 0/6，全靠重试硬扛，每次判分延迟翻倍。补上占位符后 6/6。教训是：**兜底机制
> 存在会让 Invisible 的缺失被掩盖**——重试救得了正确性，救不了延迟和成本。

**追问预案**：
1. 为什么不一开始就发现？——重试兜底太有效，功能"看起来正常"；后来靠延迟监控才暴露。
2. 300 tokens 值不值？——省掉一次完整往返（含废稿输出），净省；且延迟减半。

## Bug 4｜预生成把整个应用锁死（后台任务与交互写共存）

**现象**：上线"题目早早生成"（后台批量出题）后，用户打开题目/提交选择间歇性 500
"Internal Server Error"，前端报 JSON 解析崩溃。

**排查**：500 是纯文本 → 未处理异常。异常是 **"database is locked"**：
1. 预生成把整批 454 轮写库放在**一个长写事务**里——整个生成期间（十几分钟）持锁；
2. 连接没设 busy_timeout（默认 0ms）——交互写请求撞锁**立即失败**。

**修复**：① 预生成**逐条提交**（每题一个短事务，锁即释）；② 连接加
`busy_timeout=10000`（撞锁等待而非立即失败）；③ 前端对非 JSON 错误体给出可读提示。

**面试口播（约 30 秒）**：

> 上线批量预生成后，用户打开题目间歇性 500。排查发现是 SQLite 写锁：预生成把 400 多
> 次写库放在一个长事务里，把交互写全锁死了。修法两层：预生成改成逐条提交——每题一个
> 短事务，锁即释；连接加 busy_timeout 让撞锁等待而非立刻失败。另外我把错误提示也修了：
> 500 的纯文本体被前端按 JSON 解析，用户看到的是 [object Object] 这类乱码——现在抛的是
> 可读错误。这件事的教训是：**后台批任务和交互请求共享一个库时，事务边界就是 UX**。

**追问预案**：
1. 为什么不用队列/消息中间件？——单机 SQLite、个人版规模，进程内后台任务够用；上了多实例才需要外部队列。
2. WAL 不是支持并发吗？——WAL 解决读写并发；写-写仍是单写者，靠短事务+busy_timeout 错峰。

## Bug 5｜跨用户越权（测试抓出的真实漏洞）

**现象**：给个人版认证写测试集时，一个"应失败"的用例意外通过——
A 用户的会话能访问 B 用户的训练。

**根因**：`Training` 模型**缺 owner_user_id 字段**——数据层有归属列、代码模型没映射，
隔离校验静默失效。修复字段映射后用例即红转绿，越权通道关闭。

**面试口播（约 25 秒）**：

> 给认证写测试集的时候，我故意写了一个"应失败"的用例——结果它通过了：A 用户的会话
> 能读 B 用户的训练。根因是 Training 模型漏映射 owner 字段，数据层有归属列、
> 代码层看不见，隔离校验静默失效。修掉之后我把这类"归属字段必须映射"做成了
> schema 守卫测试。这件事的教训：**越权不是攻击者发现的，是自己用测试逼出来的**。

**追问预案**：
1. 为什么之前没发现？——功能联调全用同一个账号；水平越权只有多账号测试才能暴露。
2. 怎么防回归？——多账号隔离用例 + schema 守卫，进 CI 前先在本地全量跑。

## Bug 6｜前端三连：契约缺失的三种表现

**现象**：三个互不相关的前端问题——① 提交失败提示显示 [object Object]；
② 拖动窗口时整个内容列宽窄变化；③ 完成度百分比恒为 0。

**根因（都是"契约缺失"）**：
1. 后端 422 校验失败的 detail 是**数组**，前端按字符串拼进提示 → [object Object]；
2. 内容列 `min-width: 0`——flex 布局允许压缩到任意窄，窗口有效宽度一变整列缩；
3. 前端展示 `g.practiced/g.total`，后端分组**从未提供这两个字段** → undefined → 恒 0。

**修复**：① 错误提取兼容数组取首条；② `.main min-width: 980px` + shell 1080 + scrollbar-gutter stable——内容列恒定；③ 后端分组补 practiced/total。

**面试口播（约 25 秒）**：

> 前端三个互不相关的毛病——报错显示乱码、窗口一拖布局就缩、百分比恒为零——
> 排完发现是同一类病：**前后端契约缺失**。错误体格式没约定、布局最小宽没约定、
> 分组统计字段没提供。修法都是把契约显式化：错误提取兼容数组取首条、布局列加
> 最小宽、后端把统计字段补齐。我的标准是：**凡是靠"默契"工作的接口，都要变成
> 显式契约**。

**追问预案**：
1. 怎么系统性防这类问题？——端点响应 schema 断言（隐私字段不得出现就是从这延伸的）+ 统一错误提取层。
2. [object Object] 的完整链路？——422 detail 是对象数组 → 前端拼字符串 → toString 得到 [object Object]。

## 排查方法论（面试被问"你怎么排查"时的通用答法）

1. **先复现，再归因**：每个 bug 都先做最小复现（探针脚本/断路器测试），拿到确凿证据再动手——
   例：判分漂移先写对照实验（温度 0.2 vs 0 各 N 次），预生成锁库先在副本库复现锁等待；
2. **逐层断路**：LLM 调用装"断路器"（stub 抛错），区分"模型的问题"和"链路的问题"——
   客观题走 LLM、判分漂移都是这么定位的；
3. **数据说话**：所有结论都有实测数字（0/6→6/6、3 种组合、4/6），且标注样本量；
4. **修复必配回归钉子**：每个修复都有测试锁死（含"应失败"的负向用例），防回退；
5. **诚实边界**：没把握的标【分析】，样本小的说"初步信号"，不把推测讲成结论。

## 纪律（不能说的）

- 人工一致率 n=6 只能说"初步信号/方向"，不说一致率数字本身达标；
- 温度 0 "不足以解决漂移"是实测结论，可以说；"彻底解决"不能说；
- 跨用户越权修复是并行进行的判分批次之外独立完成的，不混在一起讲功劳。
