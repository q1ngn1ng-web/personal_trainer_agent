# 个人项目技术路线与面试讲法（2026-09-21）

> 用途：面试前 10 分钟扫一遍；回答"介绍一下你这个项目"、"技术选型怎么定的"、"遇到什么坑"时直接取用。
> **纪律**：本文件所有数字都能在仓库里复现（命令见第 6 节）；没实测的一律标注【待实测】，不要当成结论讲。

## 1. 一句话定位

**意图驱动的自适应训练 AI 教练**：用户用一句话说想学什么，系统澄清目标 → 导入资料 → 定位理解边缘 →
生成训练路径 → 每天按计划推题 → 系统判分 → 定期测验 → 达标收口。
我把"如何高效训练一项技能"这套方法论**工程化**成了可执行的代码，而且我自己每天在用。

**适配岗位的话术**：AI 应用工程 / 后端工程（LLM 编排 + 数据建模 + 规则引擎），
以及任何"需要把不确定的大模型能力包成确定产品行为"的岗位。

## 2. 三层讲法（按面试官给的时间选）

### 30 秒版

> 我做了一个自用的 AI 训练教练。用户说一句"我想学 Redis 八股"，系统会澄清目标、把资料切成语料、
> 出题定位"理解边缘"，然后排出**每道题 5 轮**（第 1/3/7/15/30 天）的训练计划；每天打开就能看到
> 今天该练哪些题，**系统出题、我作答、系统判分**，连续两次答对才算达标；每两周一次测验，
> 测验题从"练过且已过 14 天冷却期"的题库里出变式题。
> 技术上最关键的一条是：**LLM 只负责语义，状态与日期全部由规则层算**——否则模型升级一次，训练计划就漂了。

### 2 分钟版（推荐主用）

> **背景**：我想解决"用 AI 学习但学不进去"的问题。市面上的 AI 学习工具基本是问答式，
> 而我需要的是**训练**：给定资料，按记忆曲线反复练，并且能客观判定"是不是真的会了"。
>
> **产品链路**：描述 → 澄清目标（多轮追问 + 显式确认）→ 导入资料（PDF/Word/Excel/网页快照）→
> 逐知识点探测（已掌握 / 边缘 / 未达）→ 生成路径 → 排期 → 每日任务卡 → 系统判分 → 两周一次测验 → 达标。
>
> **技术路线**：Python + Streamlit + SQLite，分四层：LLM 适配层 / 领域与规则层 / 服务编排层 / 视图层。
> 三条硬约束：① **LLM 出内容、规则管状态**（日期、状态迁移、统计一律确定性代码）；
> ② **所有 LLM 输出过 JSON Schema 校验**，失败重试 → 静态降级 → 写 `llm_calls` 审计；
> ③ **客观数据不造假**——判分失败时宁可不记录，也不把故障算成"答错"。
>
> **几个能讲深的点**：排期是整条路径固定 5 轮、锚定创建日，未完成的项**累计到次日**而不是作废；
> 每道题有**跨重生成稳定的题目键**（不能用自增 id，路径重生成会把 id 换掉）；
> 测验**排除近期练过的原题**并设 14 天冷却期（否则测的只是短时记忆）；达标要求**连续 2 次通过**，
> 且判分由系统做、不让用户自己勾"我会了"。
>
> **做得最认真的一件事**：我拿自己写的代码做了一轮**代码审计**，列出 26 条问题并逐条追状态。
> 其中一条是"自我评价循环论证"：系统把"用户勾选=达标"当客观表现，再用它去裁决用户反馈，
> 结论必然自洽但毫无信息量。这类问题不审计是发现不了的。

### 5 分钟版

在 2 分钟版基础上补三块：**架构分层与数据模型**（第 4 节）、**关键选型与放弃理由**（第 5 节）、
**审计与修复闭环**（第 7 节，含具体案例）。

## 3. 技术栈与规模（现状）

| 维度 | 现状 | 说明 |
|---|---|---|
| 语言/运行时 | Python 3.12 + uv | 依赖锁在 `requirements.txt`，`uv run` 统一入口 |
| 应用框架 | Streamlit（单进程） | 第一版选它是因为"我要的是训练闭环，不是前端工程" |
| 存储 | SQLite（WAL）+ FTS5 | 19 张表（含 FTS 虚拟表），单机自用规模 |
| LLM | DeepSeek（OpenAI 兼容） | **14 个用途**（澄清 / 出题 / 判分 / 路径 / 复盘校准等），全部走同一个 `complete()` 入口 |
| 代码量 | `src/` 约 1.4 万行 | 服务层 28 个模块 |
| 测试 | 216 passed, 1 skipped, 30 subtests | `uv run pytest -q`，18 个测试文件 |
| 决策记录 | 21 条 ADR | `workspace/decisions/`，每条写"为什么选 A 不选 B" |
| 规格 | OpenSpec（1 个 store，13 个 spec/change 全绿） | 功能变更走 propose → apply → archive |

## 4. 架构分层（面试官最爱问的部分）

- **视图层** `src/ui/`：7 个页面（首页 / 新建向导 / 资料 / 路径 / 训练详情 / 今日任务卡 / 复盘）
- **服务层** `src/services/`：28 个模块——编排 + LLM 适配（plan / quiz / attempt / mastery / answer / source / edge / path / signal …）
- **领域层** `src/core/`：纯函数与数据结构（目标状态机 / 切片 / 排期 / 判定），**不碰数据库、不调模型**
- **适配层** `src/llm/`：client（重试 + 降级 + 审计）/ prompts / schema / validators / fallback
- **持久层** `src/db/`：sqlite / models / queries / tables.sql / migrate

**三个设计要点**：

1. **领域层是纯函数**：排期、达标判定、切片影响面、状态机全部可单测，不需要数据库或模型——
   所以这些逻辑是"断言覆盖"，而不是"靠模型输出的人工判断"。
2. **LLM 适配层统一出口**：所有调用走 `complete()`——统一重试、Schema 校验、静态降级、写 `llm_calls`
   （prompt 版本 / 模型 / token / 耗时 / 失败原因）。**要换模型只改一处。**
3. **服务层不依赖 Streamlit**：这是刻意的——将来把界面换成 Vue + API 时，服务层可原样复用（见第 9 节）。

## 5. 关键选型与放弃理由（面试重点）

| 决策 | 备选 | 为什么这么选 | ADR |
|---|---|---|---|
| **LLM 出内容、规则管状态** | 全 LLM 决策 / 全表单 | 日期与状态让模型生成不可复现、无法单测、模型升级就漂移；但入口又不能是表单（用户只会说一句话） | ADR-0001 |
| **不用向量库，先用 SQLite FTS5** | embedding 检索 | 单训练 1–3 份资料、切片数百级；上向量库要多出阈值校准、缓存、调用成本三类问题 | ADR-0002 / 0007 |
| **十份 md 降级为导出物** | md 作为数据源之一 | 训练项已是结构化数据，md 会变成"第二套真相"且必然分叉 | ADR-0017 |
| **路径主视图用嵌套列表，不画 mermaid** | 让模型输出流程图 | 模型不知道真实进度，图画得好看但对不上状态；进度必须来自数据库 | ADR-0009 |
| **难度由 AI 给初值 + 必附依据 + 数据校准** | 只让 AI 给档位 / 纯规则 | 单一档位无法复核，换模型就漂移；冷启动又没有真实数据 | ADR-0010 |
| **总量与单次负荷分离（覆盖/达成两种模式）** | 单一模式 | 企业培训"少练一个知识点就是没覆盖"，自定目标"达标就该收工"，一个规则表达不了 | ADR-0011 |
| **每道题固定 5 轮、锚定创建日** | 按"每周几次"排日历 | 用户要的是"这道题我练到第几次了"，不是"这周周几"；1-3-7-15-30 本身来自记忆曲线 | ADR-0021 |
| **题库用稳定题目键，不用自增 id** | 引用 `training_items.id` | 路径重生成是"先删后插"，id 会变 → 题库与计划全部悬空 | change `training-plan-and-daily-view` D7 |
| **测验排除近期原题 + 14 天冷却期** | 练过就能抽题 | 刚做完再做一遍测的是短时记忆，分数虚高反而强化"我懂了"的错觉 | ADR-0016 |
| **认证复用成熟组件、第一版只两种角色** | 自研密码会话 / 细粒度权限 | 自研容易被问穿（密码怎么存、会话怎么管、能否越权）；没有需求支撑的细粒度权限是过度设计 | ADR-0014 |

**必须标【待实测】的（不要当结论讲）**：

- 真实模型下的澄清质量、澄清完成率、平均追问轮次

## 7. 质量故事：我给自己做了一轮代码审计（强烈建议讲）

快速迭代之后我没有直接接着写功能，而是**以审计者身份过了一遍自己写的服务层**，产出 26 条结论，
分级为"必须改 / 建议改 / 可忽略"，并明确区分"我确定是 bug"与"我不确定"。最有代表性的三条：

1. **自我评价循环论证（M1）**：我原本用"用户勾选任务"→ 训练项状态 → 当作"客观表现"去裁决用户反馈。
   表面自洽，实际是**用主观当客观**：勾选即"表现好"，于是"我觉得太简单"必然触发升难度。
   更糟的是：因为客观通道永远拿不到数据，所有反馈都退化成"轻微提示"，等于功能没接上。
   **修法**：补 `practice_attempts` 逐次作答表 + 按 ADR-0015 的准确率阈值算客观口径（<3 次作答算数据不足），
   并给结构性动作找真正的执行点（难度真实改库；题量按 ADR-0021 不裁剪）。
2. **"勾选=达标"的语义混淆（M2）**：勾选同时表达"练过"和"达标"。修法是拆开——
   勾选只写 `practiced`，`passed` 只能由"连续 2 次通过"的判定写。
3. **静默截断（M4）**：探测一次只取前 8 个知识点，其余 330 个不探测也不告知。
   修法是如实告知"共 N 个、本次探 M 个"，并保留重探入口。

**为什么这条值得讲**：它展示的是工程判断力——能对自己的代码提反对意见、能区分"确定的 bug"与"待定的怀疑"、
能把结论写回仓库（审计报告 + 修复状态表），而不是留在聊天记录里。

## 8. 追问预案

| 追问 | 回答要点 |
|---|---|
| **为什么用 Streamlit 不用 Vue/React？** | 我的瓶颈是"训练闭环没打通"，不是前端工程。Streamlit 让我一天做出全流程；服务层刻意不依赖 Streamlit，将来换 Vue + FastAPI 时业务层可原样复用——后端逻辑与 UI 解耦是从一开始就守的边界。 |
| **LLM 幻觉怎么办？** | 三层防线：① 只允许基于**用户导入的资料切片**出题（训练项带 `source_chunk_ids` 回指，找不到出处就不编造）；② 所有输出过 JSON Schema + 语义校验，失败重试 → 静态降级；③ 关键状态（日期、达标、排期）不走模型。 |
| **怎么防止"用户以为自己会了"？** | 这正是核心设计：判分不交给用户（系统判分）、测验**排除近期原题**、达标要**连续 2 次**、主观信号与客观表现冲突时**以客观为主**并把差异告诉用户。 |
| **成本怎么控制？** | 出题**懒生成**（打开那道题时才生成，而不是排期时批量生成 5×N 道）；降级路径不花钱；`llm_calls` 记录 token 与耗时，可按用途算成本。**单次成本【待实测】**。 |
| **数据一致性怎么保证？** | 迁移固定套路（关隐式事务 + 关外键 + `legacy_alter_table` + 显式事务 + 迁移后 `foreign_key_check`），迁移前备份并在副本上演练；跨表引用只用**稳定业务键**（如题目键）而不是自增 id。 |
| **为什么不上 embedding / 向量库？** | 单训练资料量在数百切片级，FTS5 足够；上向量库会引入阈值校准与调用成本，收益在当前规模看不出来（ADR-0002/0007 写了触发条件）。 |
| **这个项目最难的是什么？** | 不是调模型，是**定义"什么算学会"**：验收标准怎么从"比较熟练"这种形容词变成可判定判据；以及把"客观表现"做成真实数据而不是自我评价。 |
| **做过性能/并发吗？** | 单机自用，没有并发压力。已知工程债我列在审计报告里（抓取无大小上限与 SSRF 风险、两份 DDL 会漂移）。**有意识不做**与**没意识到的坑**我会分开说。 |
| **团队协作/交付流程？** | 功能变更走"提案 → 实施 → 归档"；选型先写 ADR；每次变更写 record；量化结论必须有 evidence 出处，未实测标【待验证】。 |

## 9. 边界与未做（诚实清单）

**已实现**：目标澄清与确认、四种资料来源（粘贴/上传/网页快照/AI）、理解边缘探测（简化版）、
路径生成与预算校验、5 轮排期与累计顺延、今日任务卡（系统出题 + 系统判分）、题库与两周测验、
阶段/任务达标、四失反馈与动作执行点、UI 主题与页面骨架。

**未实现（主动说明，不要等人问）**：

- 作答**耗时**记录与基于耗时的负荷调整；难度校准（ADR-0010 的"满 3 次后按准确率校准"）
- 测验的"阶段末触发"与"重考强制换新题"
- 复盘页三个指标（信号分布 / 测验通过率 / 调整次数）
- 覆盖模式 / 达成模式的**用户选择入口**（判定逻辑已实现，`mode` 仍是默认值）
- 前端：目前是 Streamlit + 主题层；**Vue SPA + FastAPI 是规划**（服务层已 UI 无关，具备条件）
- 企业版：组织 / 角色 / 培训任务**已设计、已预留字段**，未实现

**企业版怎么讲**（依据 ADR-0019/0020，**不得说成已实现**）：
> 我把它设计成同一条代码线的 `profile` 开关而不是开分支：内容层与进度层分离（一次加工多人复用）、
> `org_id` / `scope` 字段从第一版就预留（数据隔离是事后最难补的改动）、两种角色（admin / employee）
> 够跑通"分发 → 接收 → 看报表"，认证复用成熟组件而不是自研。目前是 spec 与字段预留，实现正在推进。

## 10. 简历 bullet 建议（按岗位挑 3–5 条）

1. 独立设计并实现"意图驱动训练教练"：从目标澄清、资料解析到排期、判分、测验与达标判定的完整闭环；
   Python + SQLite + DeepSeek，216 个单测全绿。
2. 设计"LLM 只出内容、规则管状态"的分层：所有模型输出过 JSON Schema 校验 + 重试 + 静态降级，
   `llm_calls` 表留痕 prompt 版本 / token / 耗时 / 失败原因，换模型只改一处。
3. 用纯函数实现排期与判定规则（5 轮间隔阶梯、累计顺延、连续达标、验收判据比对），
   使核心逻辑在无数据库、无模型的情况下可单测覆盖。
4. 主导一轮针对自己代码的**审计**（26 条结论分级 + 修复状态追踪），发现并修复"客观表现循环论证"、
   "勾选即达标"、"影响面漏报"等隐蔽正确性问题。
5. 为多租户预留数据隔离设计（组织 / 角色 / `org_id` / 内容层与进度层分离），
   并把企业版差异收敛到 profile 开关而非代码分支。

## 11. 三条纪律（避免翻车）

1. **企业版不许说成已实现**——讲了多租户却拿不出企业数据，比不提更扣分。
2. **没实测的指标不许给数字**（完成率、准确率、成本一律【待实测】），要说就说"目前只有一次真实观察"。
3. **不夸大架构**：Streamlit 就是 Streamlit，单机 SQLite 就是单机 SQLite——
   主动说清"它在什么规模下会撞墙、下一步怎么演进"，比暗示"高并发架构"更值钱。
