# 04 · 编排框架选型：为什么不用 LangGraph / LangChain（追问完整预案）

> 场景：面试官问"这是个工作流项目，为什么不用 LangGraph / LangChain？"——本文是完整分析与口径。
> 结论先给：**选型标准是「编排复杂度 + 状态生命周期」，不是"做了 Agent 就要上 LangGraph"。**
> 本文件数字均有出处（见文末证据索引）；没有实测的标【分析】或【待实测】。
> 日期：2026-11-02（基于 `7afad59`）。

## 1. 核心分析：两种"工作流"是两种东西

| | 请求内 LLM 编排图 | 跨天业务流程（本项目） |
|---|---|---|
| 典型例子 | shopkeeper 查询链：三路并行召回 → 汇合 → 精排 → 生成，一次 HTTP 请求内跑完 | Trainer：澄清 → 排期 → 每日出题 → 判分 → 连续 2 次达标，跨越 30 天 |
| 状态活在哪 | 内存 State，一次 `invoke()` 内流转 | SQLite 业务表（`training_items` / `plan_items` / `practice_attempts`），**领域状态** |
| 谁驱动 | 图自动流转，代码一次调到底 | **用户动作**逐步触发，步与步之间隔几小时几天 |
| 有无并行/短路/循环 | 有（三路分叉、反问拒答短路） | 无——14 个 LLM 用途各自独立，拓扑是"散点"不是"图" |
| LangGraph 适合吗 | **甜点区** | **错配**：StateGraph 是"执行状态"模型，硬套会得到与领域状态机打架的第二套状态机 |

关键论据（面试展开用）：

1. **图跑不完**：Trainer 的流程被用户真实生活切成 30 天，每次调用只走一两个节点就要停下来等人；
   LangGraph 的 state 设计上是一次 invoke 内流转的，状态还得在框架格式与数据库之间搬进搬出。
2. **编排价值买不到**：本项目的编排复杂度接近零——每个 LLM 调用点就是一个函数 + JSON Schema 校验
   + 指数退避重试（统一 client `src/llm/client.py` 一层）。图框架的价值在编排，这里没有编排。
3. **可测试性是自建层的直接收益**：305 条测试全绿，核心服务用纯函数 + 临时库测试；
   换框架后这些断言要 mock 框架抽象，可测试性反而降。

## 2. 双项目对比（对"是不是不会用框架"的釜底抽薪）

| | shopkeeper | Trainer |
|---|---|---|
| 用没用 LangGraph | **用了**（查询主链 StateGraph：九节点、三路并行、条件边短路） | 没用 |
| 为什么 | 单请求内多步编排，并行分叉 + 条件短路 + 汇合正是 StateGraph 的模型 | 跨天、事件驱动、领域状态持久化、编排拓扑为散点 |
| 证明什么 | **会按场景选框架**——不是"没用过所以不用"，也不是"无脑跟框架走" |

两个项目出自同一人之手、选型相反——这本身就是答案。

## 3. LangChain 为什么更不需要

LangChain 的核心卖点是"供应商抽象 + 链式拼接"（prompt | model | parser 管道）。本项目只需要：
一个 OpenAI 兼容端点 + JSON Schema 强约束 + 指数退避重试。现状（自建薄层）换来的是：

- **可观测**：15 条 prompt 链路成功/降级/失败全落 `llm_calls`（`46ad905`），可按 prompt 版本回溯；
- **可测试**：client 一层就是全部依赖面，stub 一个函数即可；
- **可审计**：判分温度按用途配置（`temperature_for`）、失败路径不伪装成功。

套 LangChain = 在自己与 API 之间加一层别人的抽象，而它解决的问题（多供应商路由、复杂链拼接）一个都不存在。
抽象层数要与问题复杂度匹配。

## 4. 诚实边界：什么时候我会引入（主动说，防追问）

| 触发条件 | 会引入什么 |
| --- | --- |
| 后台自动推进（不依赖用户打开页面，定时跑该跑的节点） | LangGraph + checkpointer 开始有意义 |
| 单请求内出现复杂编排（多模型互馈、出题-自判-重试循环、A/B 实验图） | 重新评估 LangGraph / 自写 mini-graph |
| 需要频繁切换多家模型供应商、做路由与降级矩阵 | LangChain 式供应商抽象才有价值 |

一句话：**工具在手里，场景说了算**。我知道 checkpointer 的存在与适用条件，是按场景不选，不是不会。

## 5. 面试口径

### 30 秒背诵版

> 我的选型标准是**编排复杂度和状态生命周期**，不是"做了 Agent 就要上 LangGraph"。
> shopkeeper 查询链是请求内多步编排——三路并行、条件短路、汇合精排——LangGraph 正好匹配，我用了；
> Trainer 是跨 30 天、用户动作驱动的业务状态机，领域状态活在 SQLite，每个 LLM 调用点就是一个函数
> 加 Schema 加重试，图框架在这里买不到任何编排价值，硬套只会多出两套状态机。
> 真要做后台自动推进或 A/B 实验，我会重新评估——工具在我手里，场景说了算。

### 追问预案

| 追问 | 回答要点 |
| --- | --- |
| **你简历里管它叫"工作流"，为什么不用工作流框架？** | "工作流"描述业务形态（有步骤、有状态、有分支），不是实现工具——就像"业务有审批流"不代表必须买某个审批流引擎。我的工作流逻辑是 14 个服务 + 规则层 + SQLite 状态**显式写出来**的，每个状态迁移都能测试断言，这比包在框架里更"工作流"。 |
| **shopkeeper 用了 LangGraph，是不是双标？** | 恰恰相反，是同一把尺子量出两个结果：编排复杂度与状态生命周期不同。请求内编排图用图框架；跨天业务状态机用显式服务层。标准一致，结论不同——这比"永远用"或"永远不用"更能说明判断力。 |
| **LangGraph 有 checkpointer，可以持久化状态，你不知道吗？** | 知道，所以我把它放进触发条件里（后台自动推进场景）。但 checkpointer 存的是**图的执行状态**，我要持久化的是**领域状态**（训练项达标、作答记录、复习排期）——后者已经是数据库里的一等公民，再存一份执行快照是两套状态机互相追。 |
| **LangChain 抽象泄漏、调试成本高，这是经验还是偏见？** | 【分析】社区共识 + 保守取舍：我需要的能力面（单端点 + Schema + 重试）远小于 LangChain 的抽象面，引入它纯增依赖与间接层。我没有生产踩坑经历，所以这条讲成"工程判断"而不是"踩坑教训"——不夸大。 |
| **业务层不依赖 UI 是你守的边界（Streamlit→Vue 已验证），LLM 层为什么不留一个"可换框架"的接口？** | 已经留了——统一 client（`src/llm/client.py`）就是那层接口：14 个用途全部走 `complete()` 单入口。真要换编排框架，改动收敛在这一层和各服务的调用点，业务规则与数据模型一行不动。**薄封装本身就是"可换"的实现，不需要为此预付一个框架。** |
| **重做一遍还会这样选吗？** | 会。若重做时已知要做后台推进/A-B 实验，我会在第一版就引入 LangGraph——选型跟着需求走，不跟执念走。 |
| **编排复杂度什么时候会"涨到值得用框架"？给个具体信号。** | 三个可判定的信号：①出现需要一次 invoke 跑完的多步 LLM 互馈；②同一节点图需要 A/B 并行对比；③重试/降级策略开始出现跨节点的组合爆炸。目前 14 个用途两两独立，信号数为零。 |

## 7. 待实测（不要当结论讲）

- LangGraph checkpointer 在跨天场景的实际开销与恢复语义——未做过 PoC，只作为"触发条件"讨论，不作为"已评估"结论。
- LangChain 抽象泄漏的具体案例——无生产踩坑经历，面试中不主动举例，被追问时如实说"这是保守取舍，不是踩坑复盘"。
