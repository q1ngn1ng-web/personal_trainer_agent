# ADR-0020 个人版与企业版的功能差异用 profile 开关承载，不用 git 分支

- **状态**：已采纳
- **日期**：2026-09-20
- **关联**：修正 ADR-0019 中"超集"的表述；依赖 ADR-0011（两种模式）、ADR-0012 / ADR-0013（预留字段）

## 背景

提出过一个判断：企业版是个人版的超集，所以走同一条代码线即可。

复核后发现这个表述不准确——**企业版会砍掉个人版的一些能力**：

- 企业一般有自己的内部文档，**不需要从 URL 抓取外部资料**（外网来源反而带来内容可控性与合规问题）
- 企业培训不需要"由 AI 凭空生成资料"，因为它要求基于自家文档
- 企业版的颗粒度更粗（按章节/知识点），个人版更细（逐训练项）

于是产生一个推论：既然功能集不同，是否应该开两个 git 分支？

## 判断标准

功能差异分两类，处理方式完全不同：

| 类型 | 含义 | 处理方式 |
|---|---|---|
| **要不要用某个能力**（enablement） | 实现相同，只是一方不需要 | 配置开关 |
| **同一能力的实现方式不同**（implementation） | 同一件事要两套做法 | 才需要考虑分叉 |

## 逐项核对

| 差异 | 属于哪类 | 承载方式 |
|---|---|---|
| 企业版不需要 URL 来源 | 要不要用 | profile 禁用该资料类型 |
| 企业版不需要 AI 生成资料 | 要不要用 | profile 禁用该资料类型 |
| 默认模式（覆盖 vs 达成） | 要不要用 | 两种模式已在 ADR-0011 建成同一模型的分支 |
| 颗粒度（粗 vs 细） | 要不要用 | 同一套数据的粒度参数 |
| 鉴权与角色 | 要不要用 | `org_id` / `scope` 字段已预留 |

**结论：全部属于第一类，没有任何一处需要两套实现。**

而两个版本**共用**的部分——解析、切片、FTS5 索引、评测、调度、LLM Harness、路径生成——占了绝大部分代码量。开分支意味着这些要么复制两份，要么每次改动 cherry-pick 两遍。

## 决策

1. **不开 git 分支。** ADR-0019 的表述修正为：**个人版与企业版的功能集有交集但不相等**，仍走同一条代码线。
2. **引入 `profile`（`personal` / `enterprise`）作为功能开关集合**，差异集中在一处，不散落到业务代码。
3. **profile 控制的开关清单**：

   | 开关 | personal | enterprise |
   |---|---|---|
   | 资料类型 `web_url`（网络来源） | 启用 | **禁用** |
   | 资料类型 `ai_generated`（AI 生成） | 启用 | **禁用** |
   | 资料类型 `user_upload` / `user_paste` | 启用 | 启用（主力） |
   | 默认训练模式 | 达成（mastery） | 覆盖（coverage） |
   | 路径颗粒度 | 细（逐训练项） | 粗（按章节 / 知识点） |
   | 鉴权与角色 | 关闭 | 启用 |
   | 企业指标报表 | 不展示（但保留原始数据） | 展示 |

4. **禁用不等于删除**：企业版禁用某类来源时，代码保留，随时可开。
5. **开关必须登记**：新增开关要写进本 ADR 的清单，禁止在业务代码里散落隐式的 `if profile == ...` 判断。
6. **什么时候才真的分叉**：同一能力需要**两套实现**并长期并行维护时（私有化部署、对接企业统一身份、数据不出内网）。届时也不采用长期分支，而是独立 change + 构建产物差异；并且**公共部分必须只在一处维护**，允许分叉的只有接入层与策略层。

## 后果与验证

- **代价**：代码中需要维护 profile 判断，存在"开关蔓延"的风险（到处写 `if profile == ...`）
- **缓释**：开关集中在配置与策略层，业务模块只消费结果，不自行判断 profile
- **验证方式**：切换 profile 后，可用资料类型与默认训练模式随之变化，**且公共模块的代码零复制**——**【待实测】**
- **重评估触发条件**：出现需要两套实现的差异（如私有化部署），或某个开关在业务代码中出现超过 3 处判断，说明边界设计有问题，需要重构
