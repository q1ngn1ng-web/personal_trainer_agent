# ADR-0004 目标澄清用多轮追问，确认做成显式状态

- **状态**：已采纳
- **日期**：2026-09-19
- **关联**：OpenSpec change `goal-clarification-confirm`、`src/services/topic_validation.py`、`src/ui/page_new_training.py`

## 背景

用户描述学习内容时天然不完整："我想学虚拟语气"没有说明目标等级、周期、应用场景和验收标准。

现有实现只做一次性"主题是否具体"的二值校验，**不能追问**。结果是两个具体问题：

1. 用户要么被迫自己想清楚再填，要么被拒绝后放弃；
2. 后面"生成训练路径"缺少可信输入，只能退化成固定十要素模板。

另外，现在从输入主题到生成 10 份文件一气呵成，**没有让用户确认的环节**。

## 备选方案

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 一次性表单收全字段 | 实现最简单，字段可控 | 用户往往说不清自己要什么，等于把拆解工作还给用户，入口门槛高 | 否 |
| 一次性 LLM 出完整草案，用户直接改 | 只调一次模型，流程短 | 用户面对一份"系统替我定好的目标"，容易直接点通过，澄清变成走过场 | 否 |
| **多轮追问 + 结构化草案 + 显式确认** | 逐字段补全，用户对目标有真实的所有权 | 多轮调用增加成本与耗时；追问质量依赖 prompt | **采纳** |

## 决策

1. **澄清方式**：自由文本输入 → 多轮追问 → 结构化目标草案（5 个必填字段：内容 / 等级 / 周期 /
   每日时长 / 验收标准）。
2. **追问是否继续由规则层判定**（缺字段 且 轮次 < 5），不由 LLM 决定停止；超过 5 轮则输出
   带「系统假设」标注的草案。
3. **确认做成显式状态迁移**：`draft → pending_confirm → confirmed → active`，确认动作落库并写
   `goal_json` 快照（含 `schema_version`）与 `goal_confirmed_at`。
4. **未确认不得生成**：`draft` / `pending_confirm` 状态下不生成关键词白名单、不渲染训练文件。

## 后果与验证

- **代价**：一次澄清会话可能产生多次 LLM 调用；用户需要多答几轮；`trainings` 表增加三个字段与一次迁移
- **代价**：5 轮上限可能截断真实需要的澄清，靠"逐字段标注来源"来补偿
- **验证方式**：
  - 单测：状态迁移（合法与非法）、字段校验、追问轮次上限
  - 手动场景：输入「我想学虚拟语气」→ 至少追问 `horizon` 与 `acceptance` → 确认后数据库有快照
  - 指标：澄清完成率、平均追问轮次、草案被修改比例——**待实现后测量，当前标【待验证】**
- **重评估触发条件**：若实测平均追问轮次 ≤ 1 且草案修改率 < 10%，说明多轮追问收益不足，
  可退化为"一次成稿 + 表单修改"并新写 ADR 取代本条

---

> 本条沿用 ADR-0001 的约束：LLM 只产出草案与追问，状态迁移由规则层执行。
