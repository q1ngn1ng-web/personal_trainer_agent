# ADR-0014 认证复用成熟组件，第一版只做两种角色

- **状态**：已采纳
- **日期**：2026-09-20
- **关联**：OpenSpec change `org-and-roles`

## 背景

引入组织与角色后必须解决登录问题，可选路径差异很大：从零自研密码与会话，或复用成熟认证组件。权限模型也有粒度之分：固定两种角色，或做成可按资料、按字段授权的细粒度模型。

判断依据是**当前真实需求**与**被追问时的可辩护性**。企业场景第一版只需要跑通一条闭环：管理员发资料与任务 → 员工接收并训练 → 管理员看结果。

## 备选方案

### 认证

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 自研密码与会话 | 无外部依赖，完全可控 | 密码哈希、会话有效期、防重放、并发登录都要自己实现；**面试被追问时最容易暴露薄弱点** | 否 |
| **复用与 Streamlit 兼容的成熟认证组件** | 安全细节由成熟实现承担，精力留给权限模型与业务逻辑 | 引入依赖；组件能力边界需要确认 | **采纳** |
| 直接对接企业 SSO / LDAP | 最贴近真实企业环境 | 没有真实企业环境可对接，属于过度设计 | 暂不 |

### 权限粒度

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| **两种固定角色**（admin / employee） | 覆盖"分发—接收—看报表"闭环，模型清晰、易测 | 无法按单份资料授权 | **采纳（第一版）** |
| 细粒度权限（按资料、按字段） | 灵活 | 没有真实需求支撑的权限模型会过度设计，测试矩阵迅速膨胀 | 暂不 |

## 决策

1. 认证**复用成熟组件**，不自研密码与会话；组件隔离在适配层，业务代码不直接依赖具体实现
2. 密码只存哈希，不存明文，也不做可逆加密
3. 第一版只有 `admin` 与 `employee` 两种角色
4. **权限校验统一在服务层执行**，UI 隐藏按钮不作为权限控制手段
5. 第一版不做 SSO / LDAP / 企业微信对接

## 后果与验证

- **代价**：引入一个第三方认证依赖，更换组件时需要改适配层
- **代价**：两种角色无法表达复杂授权；若后续出现"某个员工能看某份资料"的需求，需扩展角色模型
- **验证方式**：权限矩阵单测覆盖四类越权场景（员工读他人资料、员工读他人进度、管理员跨组织读取、员工发布任务），全部预期被拒绝——**【待实测】**
- **重评估触发条件**：出现真实的按资料授权需求，或需要对接企业统一身份时，重新评估并新写 ADR
