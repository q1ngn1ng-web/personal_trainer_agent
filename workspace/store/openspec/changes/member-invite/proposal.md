# member-invite · 组织成员邀请（拉人 UI + 邀请请求 + 候选数据模型）

> **状态：已拍板待实施（四项决议 2026-11-22，见 tasks.md 文末）**。依赖：`org-and-roles`（组织与成员资格）、`plan-sharing`（已实施——
> 拉取副本时校验组织成员身份，邀请进组织后即可拉取共享计划）。
> 用户需求原话（2026-11-15）："拉人的 UI、拉人的请求、还要写表格（数据库），
> 知道哪些人能够被拉入同一个组织里面。"

## Why

组队学习的前提是**把人拉进同一个组织**。现状的成员入口只有两条，都不适配个人版组队：

1. **注册即自动进入默认组织 1**（register → provision 流程，2026-11-15 探针证实）——
   所有新用户无差别进同一个组织，没有"谁能进我的小组"的概念；
2. **企业版名单流程**（roster + issue-login）——管理员预先导入名单，按邮箱开号，
   是"公司分发培训"的形态，不是"朋友拉你进学习小组"的形态。

缺的东西：拉人的 UI、拉人的请求端点、以及**候选数据模型**——哪些人可以被拉入
这个组织、谁拉的、邀请是否已被接受。

## What Changes

* **邀请请求与数据**：`org_invites` 表记录每次邀请（邀请人 / 目标邮箱或用户 /
  角色 / 状态 / 配额归属）；成员资格沿用现成状态机 `memberships.status ∈
  invited → active / disabled`。
* **拉人 UI**：组织管理员/管理员在成员页添加成员——两种形态：
  ① 站内邀请：选择已注册用户（候选 = 已注册且非本组织成员）→ 直接建立 `invited`
  成员资格，对方下次登录可见并接受；
  ② 邀请链接/邮箱：对未注册用户生成带 token 的邀请（MVP 可先只做站内）。
* **配额托管**（对齐既有设计）：每管理员独立配额（默认 10）与删除开关（默认禁），
  组织管理员逐人设置；配额计数 = 该管理员名下 active 成员数（`memberships.invited_by`）。
* **个人版三档角色落地**（与本 change 合并实施，此前已对齐设计未实施）：
  `member / admin / org_admin`（现 `employee` 迁移为 `member`，`dept_manager` 档取消）。
* **候选数据模型**（"哪些人能被拉入"）：候选 = 已注册用户 ∧ 未是该组织在册成员；
  邀请表 + memberships 双表回答"谁拉谁、谁进了哪个组织、谁还在邀请中"。

### 关键决策（详见 design.md）

| 选择 | 备选方案 | 放弃理由 |
| --- | --- | --- |
| 邀请制（显式邀请才能进组） | 保持"注册自动进默认组织" | 组队学习需要边界与归属感；默认大锅与"我的小组"语义冲突 |
| 沿用 `memberships.status=invited` 状态机 | 独立邀请申请表 | 状态机现成；邀请本质就是"预置的成员资格" |
| 配额记在管理员身上 | 全组织总上限 | 用户拍板（2026-11-15 对齐）：逐人设置、默认 10、删除开关默认禁 |

## 非目标（后置，不进本期）

* 组织内文档四档可见性（`private/org/admins/specific`）——已对齐设计，随权限重构一起做。
* 判分链路任何改动（并行会话负责区域）。
* 组织解散/转让/跨组织多身份切换 UI。

## Impact

* `memberships` 新列：`invited_by`（配额归属）、角色值迁移（employee→member）；
  新增 `org_invites` 表（未注册邮箱的挂起邀请，可选实现）。
* `permissions.py` 角色与动作矩阵按个人版三档重写（企业版矩阵冻结于 git 历史）。
* 前端：成员管理页（添加/移除/升降/配额）+ 被邀请人「我的邀请」接受入口。
* 对外行为变化：**新注册用户不再自动进入默认组织**（需拍板，见 design 待决项）。
