# goal-clarification-confirm · 设计文档

## Context

### 背景

现有创建流程是"输入主题 → 具体性校验 → 关键词白名单 → 基线诊断 → 按十要素模板生成 10 份文件"，
**既没有确认环节，也不能追问**。

设计时先划清一条界线，避免两件事混在一起：

| 阶段 | 回答什么 | 产出 | 性质 |
|---|---|---|---|
| **澄清（本 change）** | 学什么、到什么程度、怎么算学会 | `content` / `level` / `acceptance` | **目的** |
| 路径（下一次 change） | 多久、每周几次、每次多久、分几个阶段 | `horizon` / `weekly_frequency` / `daily_budget` / 阶段与训练项 | **手段** |

澄清阶段不碰手段。用户先确认目的，再由 AI 给手段草案、由用户微调。

### 当前状态

- `src/services/topic_validation.py` 只判断主题是否"具体到可验证"，输出通过/不通过
- `trainings` 表状态：`created` / `active` / `paused` / `archived` / `failed`
- 目标信息没有结构化字段，只以自由文本 `topic` 保存
- 训练路径目前是固定十要素模板，没有已确认的目的可依赖

### 约束

- 沿用 ADR-0001：**LLM 只产出草案与信号，状态迁移由规则层执行**
- 所有 LLM 输出走 `src/llm/client.py` 统一客户端 + JSON Schema 校验 + `llm_calls` 审计
- 不新增第三方依赖；UI 沿用 Streamlit
- `data/trainer.db` 不提交 git，迁移脚本必须可重复执行

### 利益相关方

- 用户本人（自用 + 面试演示）

## Goals / Non-Goals

**Goals:**

- 用户用一句话描述学习内容，AI 只追问真正需要澄清的语义问题（≤ 3 轮，正常 ≤ 2 轮）
- 确认后的目的有快照与字段来源，可追溯、可归因
- 未确认的目的不会进入后续生成；已确认的目的可作为路径生成的唯一输入

**Non-Goals:**

- 不做训练路径生成（周期 / 频次 / 时长 / 阶段 / 训练项全部归下一次 change）
- 不做资料来源选择、达标判定
- 不做语音 / 面部等多模态输入

## Decisions

### D1 澄清阶段只产出三个字段

| 字段 | 来源 | 说明 |
|---|---|---|
| `content` | 用户输入 | 自由文本原话，不做摘要式改写 |
| `level` 目标等级 | **AI 追问** | 了解 / 会用 / 熟练 / 能讲清 |
| `acceptance` 验收标准 | **AI 追问** | 自由文本，例如「10 句改错题正确率 ≥ 80%」 |

这三个字段回答的都是「目的」。投入参数（周期、频次、每次时长）**不在本阶段出现**。

### D2 追问双限

- **软限 2 轮**：到达后给出建议值，并提示「可以直接用系统建议，也可以自己改」
- **硬限 3 轮**：到达后强制收口，输出草案并把缺失字段标为 `inferred`

需要追问的只有两项，正常路径两轮内结束。

### D3 状态机

```
draft ──提交描述──▶ pending_confirm ──用户确认──▶ confirmed
                         │  ▲
                         └──┘ 用户提出修改，重新生成草案
任意状态 ──放弃──▶ archived
```

本 change 到 `confirmed` 为止。下一次 change 在其后接续
`confirmed →（生成路径草案）→ path_pending_confirm →（用户微调并确认）→ active`。
`created` 保留给历史数据兼容，读取时按 `draft` 处理。

### D4 字段来源与不可覆盖原则

每个字段的来源写入 `goal_json.field_sources`，取值为 `user_input` / `user_reply` / `inferred`。

**AI 不得覆盖用户在界面上显式给出或已确认的值。** 这条原则在本 change 只作用于三个目的字段，
但它同时是下一次 change（路径参数微调）的前置约定——那里用户微调过的参数同样不得被 AI 覆盖。

### D5 确认必须落库，不能只是 UI 复选框

如果确认只存在于界面，后续任何一次页面刷新或重新生成都可能让"用户确认的目的"与"实际训练的目的"
发生漂移，那么后面的评测结果就无法归因——回答不了"这次达标是按哪个目的算的"。
因此确认是一次**状态迁移 + 快照写入**，由规则层执行。

### D6 LLM 输出契约（不让 LLM 决定流程）

新增用途 `goal_clarification`，Schema 输出：

```json
{
  "draft": { "content": "", "level": "", "acceptance": "" },
  "field_sources": { "level": "user_reply | inferred" },
  "missing_fields": ["acceptance"],
  "follow_up_question": "你希望怎么算学会？",
  "confidence": 0.0
}
```

**是否继续追问由规则层判定**（语义字段缺失 且 轮次 < 硬限），不由 LLM 决定停不停。
LLM 失败降级为表单式追问模板（缺哪个字段问哪个），流程不阻塞。

### D7 快照存在 `trainings`，不新建表

新增字段：`goal_json`（含 `field_sources` 与 `schema_version`）、`goal_confirmed_at`、
`clarification_rounds`。当前一个训练只有一个目的；等出现"一训练多目标"再拆独立表。

## Risks / Trade-offs

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 澄清页被误做成表单，逐步堆入参数控件 | 本 change 范围失控 | 非目标写死；参数一律留到路径阶段 |
| `acceptance` 由 AI 推断后用户不检查 | 验收标准形同虚设 | 推断字段在界面上标「系统建议」，确认页醒目提示 |
| 3 轮硬限截断真实需要的澄清 | 目的质量下降 | 草案逐字段标注来源，允许在确认页直接改 |
| 目的 JSON 结构后续变更 | 历史快照无法解析 | 快照内带 `schema_version`，读取时按版本兼容 |
| LLM 追问质量不稳定 | 用户答非所问 | 降级为表单式追问模板，且追问必须指明缺哪个字段 |
| 状态迁移写错导致训练卡住 | 用户无法继续 | 状态迁移写成纯函数并单测；非法迁移直接拒绝并记录 |
| 与历史 `created` 状态记录冲突 | 老数据无法进入新流程 | 读取时把 `created` 视为 `draft` 兼容处理 |

## 验收方式

- `uv run pytest -q`：状态迁移、追问轮次上限、字段来源标记的纯函数单测全绿
- 手动场景：输入「我想学虚拟语气」→ 追问 ≤ 2 轮 → 确认后 `trainings` 有完整 `goal_json`
  （含三个目的字段与 `field_sources`）与 `goal_confirmed_at`
- 手动场景：澄清页面上**不应出现**周期 / 频次 / 时长控件
- 指标：澄清完成率、平均追问轮次、目的草案修改率——**实现后测量，当前标【待验证】**
