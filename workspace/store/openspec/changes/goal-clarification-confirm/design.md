# goal-clarification-confirm · 设计文档

## Context

### 背景

现有创建流程是"输入主题 → 具体性校验 → 关键词白名单 → 基线诊断 → 按十要素模板生成 10 份文件"，
**全程没有让用户确认的环节**，而且第一步只做二值判定，不能追问。

进一步推演后确认：追问不该承担收参数的全部职责。用户的投入承诺（练多久、每周几次、每次多久）
有确定的取值空间，前端几秒就能选完；让 AI 一轮轮问出来，等于把设计问题推给用户。

### 当前状态

- `src/services/topic_validation.py` 只判断主题是否"具体到可验证"，输出通过/不通过
- `trainings` 表状态：`created` / `active` / `paused` / `archived` / `failed`
- 目标信息没有结构化字段，只以自由文本 `topic` 保存
- 训练路径目前是固定十要素模板，没有目标与投入参数可依赖

### 约束

- 沿用 ADR-0001：**LLM 只产出草案与信号，状态迁移由规则层执行**
- 所有 LLM 输出走 `src/llm/client.py` 统一客户端 + JSON Schema 校验 + `llm_calls` 审计
- 不新增第三方依赖；UI 沿用 Streamlit
- `data/trainer.db` 不提交 git，迁移脚本必须可重复执行

### 利益相关方

- 用户本人（自用 + 面试演示）

## Goals / Non-Goals

**Goals:**

- 用户用一句话描述学习内容，几秒钟选完投入参数，AI 只追问真正需要澄清的语义问题
- 确认后的目标有快照与字段来源，可追溯、可归因
- 未确认的目标不会进入关键词生成与文件生成

**Non-Goals:**

- 不做资料来源选择、训练路径动态生成、达标判定（后续 change）
- 不做语音 / 面部等多模态输入
- 不让 AI 自由决定训练周期

## Decisions

### D1 字段来源三分法

| 字段 | 来源 | 控件 / 说明 | 默认值 |
|---|---|---|---|
| `content` | 用户输入 | 自由文本框 | — |
| `horizon` 周期 | **前端选择** | 1 周 / 2 周 / 1 个月 / 自定日期 | 2 周 |
| `weekly_frequency` 每周次数 | **前端选择** | 2 / 3 / 5 / 7 次 | 5 次 |
| `daily_budget` 每次时长 | **前端选择** | 10 / 20 / 30 / 45 / 60 分钟 | 30 分钟 |
| `level` 目标等级 | **AI 追问** | 了解 / 会用 / 熟练 / 能讲清 | 硬限后 `inferred` |
| `acceptance` 验收标准 | **AI 追问** | 自由文本 | 硬限后 `inferred` |

AI 的职责是**用这些参数生成训练计划**（把「周期 × 每周次数」拆成阶段与训练项），
而不是决定参数本身。

### D2 追问双限

- **软限 2 轮**：到达后给出建议值，并提示「可以直接用系统建议，也可以自己改」
- **硬限 3 轮**：到达后强制收口，输出草案并标注 `inferred`

只有用户自己知道的是 `level` 与 `acceptance`，所以正常路径最多两轮就能结束。

### D3 状态机

```
draft ──提交描述──▶ pending_confirm ──用户确认──▶ confirmed ──生成──▶ active
                         │  ▲
                         └──┘ 用户提出修改，重新生成草案
任意状态 ──放弃──▶ archived
```

`created` 保留给历史数据兼容，读取时按 `draft` 处理。

### D4 参数优先级（不可违反）

```
前端显式选择  >  追问得到  >  默认值  >  AI 推断
 ui_select     user_reply    default     inferred
```

LLM 输出的字段若与用户显式给定值冲突，**丢弃 LLM 的值**，并把冲突记入日志。
所有字段来源写入 `goal_json.field_sources`，供界面显示「系统建议」标识与后续复盘。

### D5 确认必须落库，不能只是 UI 复选框

如果确认只存在于界面，后续任何一次页面刷新或重新生成都可能让"用户确认的目标"与"实际训练的目标"
发生漂移，那么第 7、8 步的评测结果就无法归因——回答不了"这次达标是按哪个目标算的"。
因此确认是一次**状态迁移 + 快照写入**，由规则层执行。

### D6 LLM 输出契约（不让 LLM 决定流程）

新增用途 `goal_clarification`，调用时把前端已选参数作为**既定输入**传入 prompt，Schema 输出：

```json
{
  "draft": { "content": "", "level": "", "horizon": "", "weekly_frequency": "", "daily_budget": "", "acceptance": "" },
  "field_sources": { "level": "user_reply | inferred" },
  "missing_fields": ["acceptance"],
  "follow_up_question": "你希望怎么算学会？",
  "confidence": 0.0
}
```

**是否继续追问由规则层判定**（语义字段缺失 且 轮次 < 硬限），不由 LLM 决定停不停。
LLM 失败降级为表单式追问模板（缺哪个语义字段问哪个），流程不阻塞。

### D7 快照存在 `trainings`，不新建表

新增字段：`goal_json`（含 `field_sources` 与 `schema_version`）、`goal_confirmed_at`、
`clarification_rounds`。当前一个训练只有一个目标；等出现"一训练多目标"再拆独立表。

## Risks / Trade-offs

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 默认值不合理，用户直接采用 | 训练强度与实际不匹配 | 记录默认值采用率；若采用率 > 80% 且事后修改率 > 30%，改为强制显式选择 |
| LLM 覆盖用户显式参数 | 用户信任受损 | 合并函数做优先级裁决，冲突写日志，单测覆盖 |
| 3 轮硬限截断真实需要的澄清 | 目标质量下降 | 草案逐字段标注来源，允许在确认页直接改 |
| 目标 JSON 结构后续变更 | 历史快照无法解析 | 快照内带 `schema_version`，读取时按版本兼容 |
| LLM 追问质量不稳定 | 用户答非所问 | 降级为表单式追问模板，且追问必须指明缺哪个字段 |
| 状态迁移写错导致训练卡住 | 用户无法继续 | 状态迁移写成纯函数并单测；非法迁移直接拒绝并记录 |
| 与历史 `created` 状态记录冲突 | 老数据无法进入新流程 | 读取时把 `created` 视为 `draft` 兼容处理 |

## 验收方式

- `uv run pytest -q`：状态迁移、参数优先级合并、追问轮次上限的纯函数单测全绿
- 手动场景：不选任何参数直接输入「我想学虚拟语气」→ 追问 ≤ 2 轮 → 确认后
  `trainings` 有完整 `goal_json`（含 `field_sources`）与 `goal_confirmed_at`
- 指标：澄清完成率、平均追问轮次、默认值采用率、事后修改率——**实现后测量，当前标【待验证】**
