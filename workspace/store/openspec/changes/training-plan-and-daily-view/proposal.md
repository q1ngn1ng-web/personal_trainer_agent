# training-plan-and-daily-view · 训练计划表与今日视图

## Why

整条链路的前半段已经通了：目的确认 → 资料 → 理解边缘 → 路径。但**路径只是"顺序"，没有"哪一天练什么"**。

`training-path-generation` 把每日排期明确列为非目标（"不做每日排期（属调度器）"，见其 `design.md:39`），
而这个"调度器"**没有任何 change 拥有它**。于是新链路用了一个临时代替品：

```
today_tasks() = 当前阶段里还没练的项，取前 5 条 + 当前阶段已通过项的前 2 条
```

这是一个**游标**，不是计划表。带来四个后果：

1. **每一天都有任务**：游标对"今天"没有任何概念，`weekly_frequency` 只参与 `预算 = 周期 × 频次 × 时长` 的一次乘法，**不参与排期**（`src/services/path_service.py:86`）。用户承诺的"每周 3 次"在系统里不存在，也没有休息日。
2. **没有入口在首页**：今日任务必须带着 `?training_id=` 进某个主题才能看到，用户要"逐个主题找今天练什么"；首页只有指标与训练列表。
3. **间隔复习失效**：复习项只从**当前阶段**的已通过项里挑 2 条，跨阶段即消失；SM-2 简化间隔（1/3/7/15/30）在新链路完全没被使用。
4. **勾选即达标**：勾选把训练项直接写成 `passed`，于是"练过"与"达标"共用一个状态，勾完当前阶段第二天直接跳阶段。

而**按日期排的复习计划本来就是需求**：已归档的 `daily-execution` spec 原文写着
「系统 SHALL 根据「复习日历」抽取**当前日期**的待办任务」与「复习项按 SM-2 简化间隔（1-3-7-15-30）……抽取」。
它当时的载体是十份 md 里的 `04_复习日历.md`；ADR-0017 把十份 md 降级为导出物之后，**这个需求的载体消失了，实现换成了游标**。
本 change 就是把载体补回来：从"文件里的复习日历"换成"数据库里的训练计划表"。

## What Changes

- 新增**训练计划表**（`plan_items`）：以**日期**为唯一排期载体，一条计划项 = （日期 × 训练 × 训练项 × 类型 new/review）
- 新增**排期生成**：在**确认路径**时生成。按 `weekly_frequency` 决定每周练哪几天、按 `daily_budget_minutes` 与训练项预计时长决定每天排几条；**不足 7 次/周就必须有休息日**
- 新增**间隔复习**：训练项被标记「练过」后，按 1/3/7/15/30 天把复习项插入计划；复习项占当日负荷有上限，不挤占新学
- 新增**首页「今日训练」**：跨训练聚合 `plan_date = 今天` 的计划项，按主题分组（"今天：Redis 持久化 3 题 + 算法 2 题"）；今日任务卡支持**跨训练视图**与**单训练视图**两种粒度
- **勾选语义收敛为「练过」**：勾选写入计划项状态与 `practiced` 标记，**`passed` 只能由达标判定写入**（达标判定属 `training-execution-feedback` 的任务 5.1）
- 新增**顺延**：当天没做完的计划项 MUST 显式出现在次日的"待补"区，**不得静默消失**；顺延还是压缩休息日由用户选（ADR-0011 决策 4）
- 训练计划改动**留痕**：重排记录触发原因（投入参数变更 / 结构性调整 / 用户手动）与前后差异
- 统一**日期口径**：排期与"当天"判定统一用本地时区（`Asia/Shanghai`），修掉现在"信号限频用 UTC 日期、打卡用本地日期"的分叉（`signal_service.py:78-79` vs `daily_log_service.py:38-39`）
- 把 `adjustment_log` 的动作接到执行点：`reduce_load` → 次日计划条数、`raise_difficulty` / `lower_difficulty` → `training_items.difficulty_tier`

### 关键取舍

| 选择 | 备选方案 | 放弃理由 |
|---|---|---|
| **数据库计划表（日期为键）** | 继续用"当前阶段游标"现算 | 游标没有"哪一天"的概念，永远每天发任务；无法回答"还剩多少、哪天练完"；无法顺延 |
| **在确认路径时一次性排出整条计划的骨架** | 每天现算明天的量 | 用户承诺的投入参数（周期/频次/时长）只在确认路径那一刻是确定的；排完才能给"哪天练完"的预期，也才能做休息日 |
| **复习项由间隔阶梯插入计划** | 把已通过项留在"当前阶段复习区" | 跨阶段即丢失，等于没有复习；间隔是既有 spec 的要求（1-3-7-15-30） |
| **勾选 = 练过，`passed` 只由达标判定写** | 勾选 = 达标（现状） | 会让"达标"这个词撒谎，且勾完即跳阶段；达标判定（连续 2 次）无处落地 |
| **未完成项显式顺延，由用户决定怎么补** | 到期自动消失 | ADR-0011 决策 4 明确"由用户决定，系统不擅自安排"；静默消失等于悄悄降低覆盖 |
| **取消老 spec 的「概念/读/写 3:4:3 硬比例」** | 保留比例约束 | 新链路的题型来自路径生成（memory / comprehension / practice / prerequisite），硬比例会与"覆盖模式必须覆盖全部必修知识点"冲突；比例改为**展示维度**而非排期约束（见 design D2） |
| **跨训练聚合视图作为主入口** | 保持"逐个主题找今日任务" | 用户心智是"打开就看今天练哪些主题的哪些题"；多主题并行时逐个找必然漏 |

详见 `workspace/decisions/ADR-0001`（排期由规则算）、`ADR-0011`（总量与单次负荷分离、顺延由用户定）、
`ADR-0017`（十份 md 是导出物，不是数据源）。

## 非目标（Non-goals）

- **不做达标判定**：`passed` 的写入规则属 `training-execution-feedback` 任务 5.1（连续 2 次达标），本 change 只把状态位置腾出来
- **不做逐次作答记录与准确率**：属该 change 的任务 1.3（`assessments` / `assessment_items`）；本 change 的客观数据仍只有"练过/未练过"
- **不做定期测验的排期**：测验进入排期是 `training-execution-feedback` 任务 4.x 的事，本 change 只保证"计划表能容纳它"（计划项有 `kind` 字段）
- **不做日历 UI（月视图 / 拖拽改期）**：第一版只做"今天"与"待补"
- **不做通知与推送**：Agent/Codex 侧每天推任务是另一个交付形态问题，需要单独决策（本 change 只保证数据层能支撑）
- **不做企业版的培训任务分配**：属 `org-and-roles` 的 `training-assignment`
- **不做跨训练的合并负荷优化**：多个训练同时排在同一天时，第一版不做总量再平衡，只展示合计
- 不引入第三方调度库（APScheduler 等）：排期是纯函数 + 表，不需要常驻调度进程

## Capabilities

### New Capabilities

- `training-plan`: 训练计划——排期生成、日期为键的计划项、间隔复习插入、顺延、计划变更留痕

### Modified Capabilities

- `daily-execution`: 改写「系统呈现今日任务卡」——数据源从复习日历文件改为训练计划表，并定义跨训练聚合视图与单训练视图（**有意不改「用户能勾选完成任务并填写三省」**，该 Requirement 正被 `training-execution-feedback` 修改，避免 delta 冲突；勾选语义写进新 capability `training-plan`）
- `progress-dashboard`: 改写「首页展示训练列表与项目说明」，在首页顶部增加「今日训练」区块

## Impact

- **代码**：`src/db/`（新增 `plan_items` 表 + 迁移）、`src/services/`（新增 `plan_service`：排期生成 / 顺延 / 重排；`path_service.today_tasks` 改为从计划表读；`schedule_service` 的老文件式抽取退场）、`src/ui/`（首页今日训练区块、任务卡支持跨训练聚合、勾选改为 `practiced`）
- **数据**：新增一张表；`training_items.status` 增加含义拆分（"练过"落 `practiced`，`passed` 留给达标判定）；老训练没有计划 → 首次进入时按当前路径生成一次（幂等）
- **依赖**：无新增第三方依赖
- **测试**：排期生成（休息日数量、每日条数不超预算）、复习间隔插入、顺延不丢项、跨训练聚合、幂等生成
- **证据**：排期与预算偏差、计划完成率、顺延次数、"预计完成日"与实际完成日的偏差——**待实测，标【待验证】**

## 与进行中 change 的协调

| change | 关系 | 处理 |
|---|---|---|
| `training-path-generation`（16/29） | 该 change 只产出顺序与阶段，明确把"哪一天练"留给调度器 | 本 change 消费它已落库的 `training_items`，不改 `path-generation` spec |
| `training-execution-feedback`（13/33） | 该 change 拥有 `learning-signal` 的动作规则与 `daily-execution` 的勾选 Requirement | **不重叠修改**：勾选语义写进 `training-plan`；动作的"执行点"落在本 change 的排期重排上，规则本身仍由 `learning-signal` 定义 |
| `understanding-edge-assessment`（12/30） | 提供逐知识点三态，是路径输入 | 无接口冲突 |
| `org-and-roles`（0/29，已后置） | 企业版"培训任务"是"谁要练"，本 change 是"哪天练什么" | 边界在 design D6 说明，不改其 spec |

**归档顺序建议**：本 change 与 `training-execution-feedback` 无 Requirement 重叠，可任意顺序归档；
但 `training-execution-feedback` 的达标判定（5.1）生效前，勾选只能写"练过"，UI 文案 MUST NOT 出现"已达标"。
