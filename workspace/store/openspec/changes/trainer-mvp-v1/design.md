# trainer-mvp-v1 · 设计文档

## Context

### 背景
个人训练师产品。从训练理论（《训练之道·十要素完整闭环 v3》、《学习的本质》）出发，落地成可执行的自用训练教练应用。

### 当前状态
- 已有理论文档：`docs/学习的本质.md`、`docs/training_ten_elements.md`、`docs/minimax-v3-SKILL.md`
- 项目已用 uv 管理 Python 环境，`.opencode/` 与 OpenSpec 工具链就绪
- 现有 `src/` 与 `workspace/` 内容为试探性 demo，本 MVP 从 0 开始设计

### 约束
- 1 周内交付 MVP
- 自用优先，通用性是加分项不是硬指标
- LLM 选 DeepSeek；存储选 SQLite；前端选 Streamlit
- 仅覆盖「人」训练对象，LLM 与动物训练不在本次范围
- 必须为后续 harness 化留伏笔（LLM 调用日志、prompt 版本化、可观测指标）

### 利益相关方
- 第一周：用户本人
- 第二阶段：朋友/试用者（局部反馈）
- 远期：GitHub 开源用户（面试项目展示、star 积累）

## Goals / Non-Goals

**Goals:**
- 让用户能完整跑通「新建训练 → 日常执行 → 周复盘」闭环
- 真实训练一个技能（Phase 1 用 asyncio/aiohttp 主题验证）
- 所有 LLM 调用可追溯（prompt 版本、模型、延迟、token、校验结果）
- 进度可视化清晰到一眼能看出"我进展到哪了"
- 训练文件（10 份 md）落盘可见，用户掌控感强
- 为面试讲故事提供"硬核点"：LLM 工程化、可观测性、数据建模、UX 设计取舍

**Non-Goals:**
- 多用户系统 / 权限 / 账号系统
- LLM 训练或动物训练分支
- 推送通知（IM 机器人、邮件、短信）
- 同伴学习匹配 / 社交功能
- 商业化 / 计费
- 移动端 App
- 完整单测覆盖率（仅核心 LLM 调用层与间隔算法预留测试接口）

## Decisions

### 决策 1：产品形态 = 本地网页（Streamlit 单页 + 多 Page）
- **理由**：1 周内交付；"说明文档 + 进展展示"刚好是 Streamlit 强项；自用阶段不需要复杂部署；后续可平滑扩展到多用户
- **替代方案**：FastAPI + 原生前端（自由度高但 2-3 天起步）、单文件 HTML（最轻量但难扩展）、IM 推送机器人（移动友好但要打通 webhook，5-7 天）

### 决策 2：对象仅限「人」
- **理由**：用户当前场景为个人技能训练；LLM 与动物训练的工程复杂度差异大，且与 MVP 时间窗口冲突
- **替代方案**：人/LLM/狗三对象并行（理论已具备但实施工作量翻倍）

### 决策 3：主题具体性校验 = LLM 判断
- **理由**：硬编码规则覆盖面有限；LLM 判断可覆盖任意主题；返回 JSON 可附带具体化建议
- **替代方案**：写死反例规则（覆盖窄，但实现快半日）

### 决策 4：关键词白名单 = LLM 自生成 + 覆盖率校验
- **理由**：主题实体抽取需要领域灵活性；强制覆盖率保证出题不跑偏
- **替代方案**：内置领域知识库（更精准但前期建设成本高）、用户手动补充（半自动，依赖用户投入）

### 决策 5：LLM 输出契约 = JSON Schema 强约束（方案 B）
- **理由**：可校验、可入库、字段稳定；契合 harness 化的可观测诉求
- **替代方案**：纯 Markdown 返回（简单但解析难）、JSON + Markdown 双产物（冗余）
- **关键澄清**：JSON 是机器看的契约，进度仪表盘从 SQLite 算，md 文件经模板渲染生成；JSON 不影响用户看到进度

### 决策 6：训练文件落盘 = md 落盘 + SQLite 元数据索引（方案 2）
- **理由**：用户能直接打开 md 文件（仪式感、可分享、git backup）；数据库提供查询与统计；md 文件是 source of truth，DB 是索引
- **替代方案**：纯入库（用户拿不到文件）、md 是真相 DB 仅缓存（读 md 要解析）

### 决策 7：进度仪表盘分层 = P0/P1/P2
- **理由**：MVP 不需要全做；分层让用户随时能看到核心进展；扩展时不破坏既有数据
  - **P0（必做）**：基线评分、已坚持天数、今日完成度
  - **P1（一周后补）**：基线升级曲线、回忆题正确率
  - **P2（远期）**：阶段目标进度、三省覆盖率

### 决策 8：内容维度 = 概念 / 读代码 / 写代码
- **理由**：覆盖知识训练的两类核心活动；可渗透到资料库、复习日历、回忆题、奖励机制四处
- **替代方案**：单一维度（"学习"作为整体粒度过粗）、四维以上（复杂度无必要）

### 决策 9：间隔算法 = MVP 用固定间隔（1-3-7-15-30），后续动态化
- **理由**：固定间隔实现简单可靠；后续可基于回忆成功率动态调整
- **替代方案**：直接上动态间隔（实现复杂、调试成本高）

### 决策 10：周复盘自动校准 = 机械计算 + LLM 裁决双层
- **理由**：机械能算的不让 LLM 算（节省 token、稳定）；需要判断的让 LLM 判断（基线升多少、要不要降级）
- **替代方案**：全 LLM 裁决（成本高、易漂移）、全机械计算（无法处理模糊调整）

### 决策 11：LLM 可观测层 = 必含 prompt_version、model、latency、tokens、validation_result
- **理由**：是 harness 化的伏笔；A/B 实验、回归测试、成本分析都依赖它
- **替代方案**：仅记录成功/失败（信息不足）、额外记录用户反馈（v2 再补）

## Risks / Trade-offs

| 风险 | 缓释 |
|---|---|
| Streamlit UI 受限，复杂交互难做 | Phase 1 自用足够；Phase 2 评估是否升级到 FastAPI |
| LLM 输出不稳定，JSON 解析失败 | Schema 校验 + 重试（最多 3 次）+ 降级提示 |
| 用户每天回来使用率低 | 奖励机制工程化 + 心流触发；Phase 1 收集自用数据再调 |
| md 落盘与 DB 双写一致性 | DB 写成功后落盘；落盘失败回滚 DB；记录失败到告警日志 |
| Phase 2 通用化时改造量大 | 设计时保留 module 边界；新增 capability 通过 spec 增量加 |
| 关键词白名单 LLM 自生成质量不稳 | 多轮生成 + 覆盖率校验 + 主题级 fallback 词典（v1.1） |
| DeepSeek API 限流/不稳定 | tenacity 指数退避重试 + 用户可见的降级提示 |
| SQLite 单点写并发问题 | 自用单用户无需考虑；Phase 2 评估切换 PostgreSQL |

## Migration Plan

本次 MVP 无既有数据迁移。首次引入：

- 初始化：`uv run python -m src.cli init-db`（创建 SQLite schema）
- 启动：`uv run streamlit run src/main.py`
- 首次训练：浏览器打开后点击"新建训练"，按向导走完一遍

回滚策略：删除 `data/trainer.db` 与 `training_<主题>/` 目录即可回到初始状态。无副作用。

## Open Questions

1. **周复盘 LLM 裁决的 JSON Schema 具体字段**——MVP 阶段先定一个最小可用版本，后续随实际使用迭代
2. **关键词白名单生成的 prompt 细节**——需要在第一次真主题跑通时调优
3. **三省输入是富文本还是结构化字段**——MVP 先用结构化字段（忠于目标/方法有效/付诸实践），后续看是否需要自由文本
4. **失败任务的重试策略**——错过一天是补做还是跳过；MVP 默认补做
5. **多训练主题的并行处理**——MVP 不实现，但 DB schema 预留 `is_active` 字段
6. **md 模板是否需要支持中英文切换**——MVP 仅中文，模板字符串集中在 `templates/` 便于将来 i18n
