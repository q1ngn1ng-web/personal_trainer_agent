# org-and-roles · 设计文档

## Context

### 背景

现有设计全部是单人视角：一个人确认目的、选资料、生成路径、训练、达标。

企业场景多出三层关系：

1. **组织归属**：用户属于某个组织
2. **角色差异**：管理层发资料、看结果；员工接收、练自己的
3. **分发关系**：一份资料被多名员工使用，一份训练任务覆盖一批人

这三层关系同时带来一个技术收益：**内容只需加工一次**（见 ADR-0013）。

### 当前状态

- `training-source-selection` 已预留 `sources.org_id` 与 `sources.scope`
- 其余表（训练、路径、训练项、作答）都还没有组织维度
- 系统没有任何用户与登录概念

### 约束

- 沿用 ADR-0001：权限与状态判定由规则层执行
- 沿用 ADR-0013：内容层按组织存一份，进度层按人存
- 不自研密码体系（ADR-0014）
- 当前 UI 是 Streamlit，认证方案需与之兼容

### 利益相关方

- 管理层（`admin`）：上传资料、发布培训任务、查看达标情况
- 员工（`employee`）：接收培训、完成训练、查看自己的进度
- 用户本人：演示与面试讲解

## Goals / Non-Goals

**Goals:**

- 管理层能把资料放进企业公共区，并发布成带验收标准与截止日期的培训任务
- 员工登录后能看到"我要练什么、练到哪了"，且只能看到自己的进度
- 组织之间数据完全隔离，跨组织不可见
- 能算出首次达标周期、必修覆盖率、首次通过率

**Non-Goals:**

- 不做 SSO、组织加盟、细粒度权限、HR 系统对接
- 不做部门树

## Decisions

### D1 数据模型

```
organizations
  id, name, created_at

users
  id, org_id, email, display_name, password_hash, created_at, last_login_at

memberships
  id, user_id, org_id, role(admin|employee), tags(JSON), created_at

assignments                        -- 培训任务（内容层 + 派发规则）
  id, org_id, created_by, title,
  source_ids(JSON), acceptance, mode(coverage|mastery),
  due_at, created_at, status(draft|published|archived)

assignment_targets                 -- 目标人群
  id, assignment_id, target_type(all|tag|user), target_value

assignment_receipts                -- 接收与进度（进度层）
  id, assignment_id, user_id, training_id,
  received_at, first_passed_at, completed_at, status
```

**既有表一律补 `org_id`**（`trainings`、`training_paths`、`training_items` 等），
即使当前只存在一个组织。这与 `training-source-selection` 预留 `sources.org_id` 是同一个理由：
数据隔离是事后最难补的改动。

### D2 认证方案

见 `ADR-0014`。要点：

1. 复用与 Streamlit 兼容的成熟认证组件，**不自研密码与会话**
2. 密码只存哈希，不存明文，也不做可逆加密
3. 会话有效期与登出由组件负责
4. 第一版不做 SSO

### D3 权限校验统一在服务层，UI 不算权限

| 对象 | 规则 |
|---|---|
| 资料读取 | `personal` 仅本人；`org_shared` 限同组织 |
| 训练与进度读取 | 员工仅本人；`admin` 可读本组织汇总与明细 |
| 资料写入、任务发布 | 仅 `admin` |
| 跨组织访问 | 一律拒绝 |

**必须落在服务层**：UI 隐藏按钮不算权限控制，服务函数才是唯一可信的校验点。
每条服务函数入口都校验 `org_id` 与角色，校验失败抛统一异常。

### D4 资料可见范围与分发

| scope | 谁能上传 | 谁能使用 |
|---|---|---|
| `personal` | 员工本人 | 仅本人 |
| `org_shared` | 仅 `admin` | 本组织全部成员 |

### D5 培训任务：把资料变成可量化培训的最小单位

发布任务时确定四件事：**资料范围**（`source_ids`）、**验收标准**、**目标人群**、**截止日期**。

员工接收后：

1. 系统创建属于该员工的训练
2. 目的字段由任务填充，`field_sources` 标记为 `assigned`
3. 员工补充个人化投入参数（周期 / 频次 / 每次时长），或直接采用系统建议
4. 路径生成沿用 `training-path-generation` 的正常流程

**任务派发与用户自述的区别**：前者目的在于任务本身（"必须掌握这些内容"），后者目的来自自然语言描述。
本 change 只在规格中写明"任务派发时目的由任务填充"，不改 `goal-clarification` 的规格。

### D6 内容层与进度层的落地（ADR-0013）

| 层 | 表 | 粒度 |
|---|---|---|
| 内容层 | `sources`、`source_chunks`、`training_items` 的题干/答案/关键句/结构难度/来源回指 | 组织一份 |
| 进度层 | `assignment_receipts`、作答记录、评测结果、经验难度、完成状态、路径进度 | 每人一份 |

**为什么必须分开**：同一道题对老员工容易、对新员工难（难度是「题目 × 学习者」的关系）。
混在一起会让统计失真，也会把个人数据暴露给他人。

**新人冷启动**：经验难度可按人群（`memberships.tags`）聚合，但需设**最小样本量**（首版 5 人），
低于样本量时回退到结构难度。

### D7 企业价值指标的口径

| 指标 | 口径 | 统计时机 |
|---|---|---|
| 首次达标周期 | 从 `received_at` 到 `first_passed_at` 的自然天数，按人中位数 | 每次达标时写入，报表按时段聚合 |
| 必修覆盖率 | 完成全部必修训练项的人数 ÷ 目标人群人数 | 实时计算 |
| 首次通过率 | 首次考核即达标的人数 ÷ 参加考核人数 | 每次考核后计算 |

**口径必须写死在文档里**，否则同一份报表换个算法就变了——这与 `workspace/evidence/` 的要求一致。

### D8 员工视角的界面收敛

员工登录后只看到三样：**待办**（今天要练什么）、**进度**（还剩多少、哪几项已达标）、**我的资料**（个人资料）。
管理端只看到四样：**资料库**（含企业公共区）、**任务**（发布与状态）、**人员**、**报表**。

**刻意不做**：员工之间互看、排行榜。理由：训练数据属于个人，用排名做激励会诱导刷量而不是掌握。

## Risks / Trade-offs

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 组织隔离漏做某张表 | 跨组织数据泄露 | 每张表强制 `org_id` + 单测覆盖"跨组织不可读" |
| 越权通过 UI 绕过 | 安全漏洞 | 校验只在服务层，UI 隐藏按钮不作为控制手段；补权限矩阵单测 |
| 认证组件选型不当 | 后期换栈成本高 | 选型见 ADR-0014；把认证隔离在适配层，业务代码不直接依赖具体组件 |
| 人群标签不维护 | 任务派发对象错 | 标签默认从 `memberships.tags` 取，任务发布时展示命中人数供确认 |
| 小样本聚合经验难度 | 统计噪声导致难度失真 | 设最小样本量（5 人），不足时回退结构难度 |
| 指标口径漂移 | 报表前后不一致 | 口径写进文档与代码常量，报表同时展示口径说明 |
| 范围膨胀 | 项目做不完 | 非目标写死（不做 SSO / 部门树 / 细粒度权限 / HR 对接） |

## 验收方式

- 单测：权限矩阵（员工读他人资料被拒、管理员跨组织被拒）、任务目标人群匹配、三个指标的口径计算
- 手动场景：管理员上传一份资料到企业公共区并发布任务 → 员工登录后能看到任务并开始训练 → 进度只对自己可见
- 手动场景：员工尝试访问另一个组织的训练，应被拒绝
- 指标：验证三个指标能算出真实数值（可用构造数据先跑通口径）——**真实性待实测，当前标【待验证】**
