# 20261029 时间成本基准（判分/检索/LLM 调用画像）

> 触发：简历业务价值梳理——需要把「确定性判分」从机制描述升级为可复现的时间/成本账。
> 工具：`scripts/benchmark_time_cost.py`（本次新增，只读，不写库）。
> 数据来源：本机实测（规则判分、FTS5）+ `data/trainer.db` 的 `llm_calls` 历史记录与计数，非构造数据。

## 结论

1. **规则判分路径实测微秒级**：选择题 0.0012 ms/次、填空题 0.0016 ms/次、主观题要点聚合 0.0045 ms/次（N=10000），全程零模型调用。
2. **LLM 语义评分类调用（同库对照）秒级**：`baseline_scoring` 平均 6.3s（1.9-12.5s）——同为「给作答打分」这一动作，规则路径与模型路径相差约 6 个数量级。
3. **本地 FTS5 检索 p50 0.054ms / p95 0.091ms**（369 条真实切片）——检索不是本系统的耗时瓶颈，性能叙事不应落在检索上。
4. **题目幂等落库**：21 个计划项已带题（首轮生成后，第 2 轮起打开零生成等待）。

### 可引申的方案测算（性质：测算，非实测）

一条 30 天训练约 97 个训练项 × 5 轮 ≈ 485 次判分；其中客观题按当前分流全部走规则路径（0 次模型调用）。若全部判分走模型，按库内语义评分类调用均值 6.3s/次估算，仅判分环节即引入约 485 × 6.3s 的模型等待与对应 token 成本。**引用时必须标明「测算」**，且只覆盖客观题口径。

## 数据边界与引用规则

- `llm_calls` 现有 40 条记录全部为**建库阶段（开发期）**数据，n 小、非生产样本——只能做量级对比（秒级 vs 微秒级），**不得引用百分比结论**（如「延迟降低 99.99%」）。
- 规则判分耗时为本机实测，机器规格不同数值会变；跨机引用时以「微秒级/毫秒以下」的量级表述为准。
- 主观题的 LLM 要点判定延迟**未单测**（当前 `llm_calls` 无 grading purpose 记录）；如需该数字，须先在主链接入 `llm_calls` 记录（对应素材库「LLM 调用审计不完整」缺口）。
- 效果类指标（坚持率、学习提升）不在本基准范围内，且当前无采集，不得引用。

## LLM 实测追加（2026-10-29，阿里云免费额度端点）

> 工具：`scripts/eval_grading_memory_cost.py`（本次新增）。为不消耗 Trainer 自身的 DeepSeek 付费 token，
> 通过 `DEEPSEEK_BASE_URL` 环境变量把**项目真实代码路径**指向阿里云兼容端点的免费额度模型
> `deepseek-v4.1-flash`（1M 免费额度，有效期 2027-01-17）。全程未写入任何数据库（实测后核对 `llm_calls` 仍为 40 条）。

### 样本

真实库 `plan_item #235`（training=69「Redis 八股冲刺」，item=905eeb61eba2），出题时固化的要点清单 3 条（RDB 触发时机 / AOF 追加日志 / 持久化选型），作答为一个含部分错误观点的回答。

### 臂 A｜项目真实路径 `complete("quiz_grade")`（含 Schema 校验与错误反馈重试），n=3

| run | tokens_in | tokens_out | 延迟 | 重试 | 逐条判定 |
|---|---|---|---|---|---|
| 1 | 918 | 387 | 2.8s | 1 | 3 条（hit/partial/missing + 各自 reason） |
| 2 | 1004 | 1249 | 9.1s | 1 | 3 条 |
| 3 | 944 | 607 | 5.1s | 1 | 3 条 |

**关键观察**：3 次运行全部发生 1 次重试——模型首发输出 100% 不合 Schema（缺 `reason`/`results`，多 `points`/`is_correct` 字段），被 JSON Schema 拦截后携带错误反馈重试，**3/3 恢复合规**。配套的直调对照（不重试）6/6 首发不合规。这把「LLM 调用治理」从设计描述升级为量化事实：**没有 Schema 拦截 + 重试，判分链路一次都跑不通**。

### 臂 B｜学习者记忆上下文注入的 token 成本（直调，n=3×2）

- 判分 prompt 净输入成本（首次调用、含注入的 Schema）：**532 tokens**（3 次完全一致）。
- 注入 `render_context` 输出的四段式记忆上下文（真实库当前 ≈14 tokens）：tokens_in 552——**每次调用增量 ≈+20 tokens（约 4%）**。
- 直调 6/6 首发不合规（与臂 A 互证）；本项目路径由重试兜底。

### 记忆模块存取速度（纯 SQL，零模型调用）

| 函数 | 真实库（4 次作答样本） | 种子库（300 次作答 × 12 知识点 × 3 题型） |
|---|---|---|
| knowledge_profile（薄弱点画像） | 0.012 ms | 0.441 ms |
| mistake_reason_counts（错因分布） | 0.006 ms | — |
| recent_mistake_notes（最近错因） | 0.008 ms | — |
| recommended_type_mix（题型配比） | 0.014 ms | 0.466 ms |
| render_context（四段式渲染） | 0.042 ms | 2.396 ms |

种子库上 `render_context` 输出 ≈98 tokens，对照「原始作答全量塞入」基线 ≈7201 tokens——**压缩比 0.014**，即"记住用户哪儿不行"的上下文成本被压到原始历史的 1.4%，且不随训练时长线性增长（按需聚合、逐段封顶）。

### 边界

- 延迟数字来自阿里云免费端点，只作该端点参考，不与 DeepSeek 直连的 `llm_calls` 历史混算；token 数是可迁移口径。
- 记忆上下文当前真实样本仅 4 次作答（14 tokens）；压缩比 0.014 来自种子数据（random.seed(42) 可复现），属**机制演示**，不是真实 30 天使用数据。
- `render_context`/`recommended_type_mix` 目前仅被测试调用，**尚未接入生产判分/出题 prompt**（quiz_grade 现注入的是题目+参考答案+要点+作答，无记忆上下文）——臂 B 是"若接入"的模拟注入实测，简历不得写成已生效。**（状态更新：同日晚已完成判分侧接线，见下节）**
- 主观题一次判分的完整 token 账（含被拦截的首发输出）：输入 ~532（首发）+ ~950（重试请求，含错误反馈与首次输出回显）+ 输出 387-1249；其中首发输出被拦截即浪费部分，这正是重试机制的保险成本。
