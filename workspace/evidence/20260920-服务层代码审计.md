## 1. 必须改

### M1. 四失反馈的闭环实际没闭合：客观通道恒为 `unknown`，动作也没有任何消费者

**现象**：用户在今日任务卡点「太简单/太难/太多了/太窄了」，系统只回一句文案，难度、题量、范围、路径**都不会真的改变**。

**证据**

- 客观状态只有一个来源，而 UI 恒传 `None`：`src/ui/page_daily.py:193-195`（`item_status=None`）→ `src/services/signal_service.py:239-244`（`objective=objective_state(item_status)`）→ `src/services/signal_service.py:86-92`（`None` → `"unknown"`）。
- `decide()` 的分支顺序决定了 `unknown` 会**抢先短路**：`src/services/signal_service.py:130-138` 位于 `139`（同类阈值）与 `148`（每日限频）之前，所以阈值分支在运行期不可达。
- 实测（`/tmp/audit_sim.db`，`same_signal_today=9, structural_today=9` 的极端输入下）：

```
objective_state(None) = unknown
  too_easy:  action=light_hint applied=True
  too_hard:  action=light_hint applied=True
  too_much:  action=light_hint applied=True
  too_narrow:action=light_hint applied=True
```

- `action` 的四个取值（`reduce_load` / `raise_difficulty` / `expand_scope` / `lower_difficulty`）在 `src/` 里**只出现在 `signal_service.py` 自己**（`rg -n "reduce_load|raise_difficulty|expand_scope|lower_difficulty" src/ tests/` 去掉 signal_service 后无命中）；`adjustment_log` 除插入/列表/级联删除外无消费者。

**对 AUDIT-BRIEF 第 1 条的正面回答**：**你怀疑的「客观表现循环论证」在运行期不成立——但原因不是它没问题，而是那条分支压根跑不到。**

1. `page_daily` 恒传 `item_status=None`，所以 `objective == "low"/"high"` 的两个冲突分支（`signal_service.py:111-129`）是**死代码**；
2. 就算接上真实状态，用 `training_items.status` 当客观表现确实是循环的：`status` 由勾选写入（`page_daily.py:93-95` → `path_service.mark_item`），勾选即 `passed`，于是「自评太简单」必然命中 `objective=high` 并升难度——与 ADR-0015 要求的「准确率 + 作答次数 ≥ 3」完全不是一回事。

**影响**：ADR-0015 的三条硬约束（准确率口径、冲突裁决、限频）在运行期**一条都没生效**；单测用合成的 `objective` 值把这件事盖住了（`tests/test_signal_service.py:26-57` 全是 `decide()` 直调）。用户会以为系统在按他的反馈调整，实际只是留痕。

**建议**（按成本从低到高）

1. 最低成本且不撒谎：本条通道未接通前，把「已调整」改成「已记录，需要更多作答数据才能调整」，并在 UI 标注**本轮只做轻微调整**；
2. 中期：答作记录表落地后，`objective` 改取近 N 次作答题准确率（ADR-0015 的 0.6/0.9 口径），`item_status` 不再参与；
3. 结构性动作必须有执行点（改 `training_items.difficulty_tier` / 次日任务条数），否则 `applied=True` 是假话；
4. 补一条**集成测试**：从「UI 传参 → `process_signal` → `decision.action`」断言，而不是只测纯函数。

**确定性**：确定是 bug（设计意图与运行期行为不一致）。

### M2. 「勾选 = 达标」：既语义错，又让复习机制整体失效

**现象**：勾选今日任务把训练项直接写成 `passed`；把当前阶段的项勾完，第二天今日任务**跳到下一阶段**，且**之前阶段的项再也不会出现**（不是"复习到期"，而是彻底消失）。

**证据**

- 勾选即 `passed`：`src/ui/page_daily.py:86-95`（`mark_item(int(task_id[1:]), "passed")`）。
- 取消勾选写回 `pending`（`page_daily.py:94`），`passed` 记录被抹掉：`src/services/path_service.py:584-600`。
- 「今天练什么」= 当前阶段待练 + **当前阶段**已通过项的前 2 个：`src/services/path_service.py:565-581`；当前阶段 = 第一个还有 `pending/in_progress` 的阶段：`src/services/path_service.py:548-562`。
- 实测（临时库，两阶段各 2 项）：

```
today(未勾选):        {'new': [1, 2], 'review': []}
today(阶段1勾完):     {'new': [(3, 'j3'), (4, 'j4')], 'review': []}   ← 阶段1的两项再没出现
current_stage:        阶段2
```

- 间隔复习参数（`STANDARD_INTERVALS = [1,3,7,15,30]`，`src/services/schedule_service.py:15`）只作用于老的文件式 `trainings.schedule`；新链路 `schedule` 为空、走 DB 分支（`schedule_service.py:153-188`），**完全没用上**。

**影响**：① 训练项状态同时承担"练过"和"达标"两种语义，`passed` 失去含义；② 复习（本项目的核心方法论之一）在新链路实际不存在；③ ADR-0010 要求的"连续 2 次达标"无处落地；④ 顺手一点取消勾选就丢完成记录。

**建议**（最小且不撒谎）

1. 状态枚举拆语义：`pending / practiced / passed`（`passed` 只由达标判定写入），勾选写 `practiced`（`tables.sql:209` 的 CHECK 需重建表，属本文件已知风险）；
2. `today_tasks` 的 `review` 改成「按 `last_practiced_at` + 间隔到期」从**所有阶段**取，而不是从当前阶段的 `passed` 取；
3. 达标判定落地前，UI 文案把「✅ 已达标」改成「✅ 今天练过」（`page_path.py:20` 的状态标签），避免术语过度承诺。

**确定性**：确定是 bug（行为与 ADR-0010/HANDOFF 第 4 节的语义约束冲突）；其中"到底该不该有连续 2 次达标"需要你确认（见 Q4）。

### M3. 刷新网页快照 / 重新解析后，训练项出处静默失效，且清理函数从未被调用

**现象**：资料重解析会先删光该来源的切片再重插（新 `id`），而训练项里存的是旧 `id`；清理悬空回指的 `validate_item_chunk_links()` 没有任何调用方。路径页的「出处」就这样静默消失。

**证据**

- 先删后插：`src/services/source_service.py:134-144`；
- `refresh_snapshot` 直接 `parse_source(force=True)`：`src/services/source_service.py:375-404`（无影响面、无回指清理）；
- `parse_source` 内容变化时同样整体替换切片：`src/services/source_service.py:147-195`；
- `validate_item_chunk_links` 只有定义，`src/` 内无调用方：`src/services/path_service.py:518-545`（`rg` 仅命中 `tests/test_path_service.py:184`）；
- 与 change 的验收不一致：`workspace/store/openspec/changes/training-source-selection/tasks.md:95` 把「B1.5 手动刷新快照：重新抓取后走增量重建与影响面流程」标成了 `[x]`，但 `compute_impact` 在 `src/` 内同样**只有定义与测试、没有页面入口**（`source_service.py:445-467`）。
- 真实库存在这种数据：`source_chunks` 346 行、`training_items` 27 行，任一次刷新都会让回指变悬空。

**影响**：A4.1「训练项可追溯到原文」在刷新/重解析后失效，且**不报错**（`page_path.py:72-75` 找不到出处就跳过渲染）。注意 `source_chunks.id` 是 `AUTOINCREMENT`，所以是"悬空"而不是"指错"，风险因此限于"丢证据"。

**建议**：`refresh_snapshot` / `parse_source` 之后调用 `validate_item_chunk_links`，并在有影响面时把 `compute_impact` 的清单显示给用户（proposal 的"由用户决定保留还是重练"）。

**确定性**：确定是 bug（代码行为与已标 `[x]` 的验收项不符）。

### M4. 知识探测只取"前 8 个"且静默截断

**现象**：一次探测最多覆盖 8 个标题（按切片插入顺序），超出部分既不探测、也不告知用户。

**证据**

- `MAX_KNOWLEDGE_POINTS = 8`、`if len(points) >= limit: break`：`src/services/edge_service.py:26`、`src/services/edge_service.py:90-127`；
- 切片顺序：`edge_service.py:97-105` 是 `ORDER BY c.id`（即导入顺序 = 资料开头优先）；
- 真实库实测（只读）：

```
training 24  https://blog.csdn.net/... 切片 327，去重标题路径 319
training 42  Redis 持久化八股文.pdf    切片  19，去重标题路径  19
全部去重标题路径数 338  → 探测上限 8 时漏掉 330
```

**影响**：路径生成把"边缘"当输入（`path_service._fallback_skeleton`），但它只拿到前 8 个知识点的三态；剩下 330 个知识点既没被判"已掌握"（跳过）、也没被判"未达"（前置），直接不进任何阶段——用户看到的是**看起来完整、实际只覆盖 2% 标题的路径**，且没有任何提示。

**建议**：① 立刻把「共 N 个知识点，本次只探测 8 个」显式展示；② 让用户选章节/范围，或改成按章节抽样（每个一级标题取代表）；③ 长期按 ADR-0018 的"章节级粒度"降载——319 个标题本身说明颗粒度太细（每个 `<h1..h6>` 都成了知识点，`src/services/web_source.py:29,76-79`）。

**确定性**：确定是行为缺陷（静默截断）。

### M5. 三态结论依赖模型自报难度，且模型故障时整体倒向"未达"

**现象**：判定的唯一开关是模型给的 `difficulty`；同一个知识点两次探测拿到不同难度就会给出不同三态。更严重的是，评分调用失败时**全部按 `fail` 处理**——此时三态完全由题目难度决定（兜底题目固定难度 2 → 清一色 `unreached`；模型出的题多为 3-4 → 清一色 `edge`），**结论由一次基础设施故障决定，而不是由学习者决定**。

**证据**

- 难度来自 LLM 输出的原值：`src/services/edge_service.py:179-191`（`int(raw.get("difficulty", 1) or 1)`）；
- schema 里**没有** `basis`，且 `additionalProperties: False`：`src/llm/schema.py:192-220`（`edge_probe`）、`src/llm/schema.py:244-285`（`path_skeleton`）——ADR-0010 决策 2 要求的"必附依据、缺失即拒绝重试"在 schema 层就被排除了；
- 判定规则：`src/services/edge_service.py:247-257`；
- 故障即 `fail`：`src/services/edge_service.py:227-243`（`item.verdict = "fail"`、`reason="未能取得评定结果，按未通过处理"`），兜底题目难度固定 2（`edge_service.py:193-204`）；
- 实测 `judge_state` 的形状：

```
judge_state('pass', 1..4) = ['edge',     'edge',     'mastered', 'mastered']
judge_state('fail', 1..4) = ['unreached','unreached','edge',     'edge']
```

**影响**：① 一次上游故障 → 全部按"答错"处理：题目来自兜底时路径变成清一色「前置铺垫」（`path_service.py:182-209`），题目来自模型时全部落"边缘"→ 整份内容都被当教学重点；两种都是"符合格式但完全错误"的路径；② 难度只取模型一个整数，没有区间/依据/稳定性约束，ADR-0010 的"AI 给初值 + 必附依据"只落实了前半句。

**建议**

1. 把"评估未取得"与"答错"分开：新增 `verdict='unknown'`（表已有该枚举，`tables.sql:157`）→ `state=NULL` → 不参与"未达"前置；
2. 单题口径下用确定性规则替代模型难度：按题型/切片来源固定档（如"直接回忆=1、需要推理=3"），或答对=`mastered`（单题信息量下的保守上限）、答错=低档题→`unreached`、非低档→`edge`；
3. 若坚持用模型难度：schema 补 `basis` 并做区间校验，或让 `judge_state` 接收"难度区间"而不是单点值。

**确定性**：①（故障即全未达）确定是 bug；②（单题用模型单点难度判三态）是确定的设计弱项，改成什么口径需要你定（见 Q…下文 Q3）。

## 8. 已知局限
